# 追光缉盗 Light Chase 项目 Outline 调研报告

调研日期：2026年10月7日。开发约束：Android Studio、Java。项目状态：选题和设计阶段，尚未完成游戏实现、设备测试或玩家实验。

## 1 调研结论与交付状态

建议继续这一选题，并将首版限定为 **2D俯视角、1名警察对1名小偷、局域网双手机、1张地图、3组取送任务、2种道具、本地战绩**。项目的主要价值是有限信息下的追踪与路线博弈。加入实时联机后，难度属于中等偏上；是否适合小组，要由第一阶段的设备联机验证和实际可用工时决定。

创新论述应使用“对已有机制的原创组合与改进”，不要使用“全球首创”。隐身、非对称对抗、潜行搬运和烟雾均已有先例；本项目拟突出持续照明标记、受击后的逃脱窗口，以及多组取送任务对搜捕路线的影响。

本轮材料包括4页英文Project Summary、14页英文PPT、这份中文调研报告。英文是根据课程材料语言作出的工作假设，不代表已确认的提交语言。当前教学周、组员名单与人数、仓库地址尚未提供；周计划暂以第6周开始演示，需要在提交前替换为真实周次。文件是可审阅的Outline草案，尚未向Moodle提交。

本次对竞品的判断来自官方商店和项目文档，没有把网上资料分析写成亲自试玩结果，也没有开展用户访谈。生成的界面图是概念示意，不是运行截图、最终关卡图或已测试的可达性证明。

## 3 相关应用调研和创新边界

### 3.1 Robbery Bob — King of Sneak

官方页面描述了单人潜行解谜、收集物品、躲避警卫和多种地图。商店画面可观察到俯视关卡和触摸操作。与本项目的直接联系是“规划行进路线、避开发现、获取目标物品”。[官方Google Play页面](https://play.google.com/store/apps/details?id=com.chillingo.robberybobfree.android.row&hl=en)

拟借鉴的是清晰的空间关系、简单操作和潜行节奏。拟改进为真人警察根据有限视野主动搜索，小偷不只是一次取走物品，还要权衡不同取送路线。这里“改进”指符合本项目目标的新体验，不是认定原游戏质量较差。不能把其中的素材或源码当成开源资源。

### 3.2 Identity V 第五人格

官方页面明确介绍1对4非对称玩法：求生者躲避追击、解码并逃生，监管者追捕；还有不同角色。它提供了“双方目标和能力不相同”的直接参照。[官方Google Play页面](https://play.google.com/store/apps/details?id=com.netease.idv.googleplay&hl=en)

本项目拟保留角色目标的对立，缩减为1对1、俯视2D、一套基础角色。主要判断从接触/攻击追捕转为方向、遮挡和持续照明；任务从固定地点的进度推进转为取送路线。减少角色和队伍规模是课程范围控制，不能单独当作技术创新。

### 3.3 Burgle Bros

官方页面介绍团队劫案、规划、警卫、不同角色能力、跨楼层移动，以及烟雾、EMP等道具。它说明“潜行＋任务路线＋工具”本身已有成熟先例。[官方Google Play页面](https://play.google.com/store/apps/details?id=net.fowers.BurgleBros&hl=en)

本项目拟借鉴地图路线与道具时机之间的关系，把对抗方交给另一名玩家，并围绕连续照明与有限时间组织节奏。首版只保留一层地图和两种工具。烟雾本身不算本项目原创；原创工作在于它怎样与视线、标记计时和取送任务共同作用。

### 3.4 必须补充的近似机制 Invisigun Reloaded

开发者在Steam页面说明了隐形角色、本地/在线多人、脚印和环境扰动线索。它是判断创新边界的重要先例，不能因为它不属于前三款Android竞品就忽略。[开发者Steam商店页面](https://store.steampowered.com/app/375750/Invisigun_Reloaded/)

因此，不建议宣称“第一次把隐身加入多人对战”。可以提出的设计差异是：本项目围绕搜捕与搬运两个不对称目标，用持续照明判定抓捕，第一次和第二次被标记后给予明确逃脱窗口。有限调研不能证明市场上没有其他同类组合。

### 3.5 新旧功能对照

| 已有设计基础 | 本项目拟增加或改变 | 玩家价值假设 | 如何验证 |
|---|---|---|---|
| 单人潜行与警卫 | 真人警察控制照明搜索 | 对手会调整策略，增加重复游玩变化 | 换边试玩，记录路线是否单一、警察是否只是盲走 |

## 4 推荐的首版规则

以下全部是拟定参数，未经平衡性验证。开发时集中放入配置，不写死在多个界面中。

| 项目 | 首版设定 |
|---|---|
| 对局 | 1警察对1小偷；180秒；一张约24×18格的固定地图 |
| 小偷胜利 | 完成A→A′、B→B′、C→C′三组交付，再在任一出口完成1秒交互 |
| 警察胜利 | 累计3次有效标记，或倒计时结束 |
| 携带 | 同时最多1件；取件、交付和撤离均需站定1秒；移动或被标记取消当前交互 |
| 初始速度 | 警察3.2格/秒；小偷空手3.4、携带3.0格/秒；只是待测试起点 |
| 警察信息 | 始终知道静态墙和站点；灯内且无遮挡才可见小偷；不获得小偷当前任务或隐蔽取件事件 |
| 小偷信息 | 始终知道静态地图与自己的任务；在约6格且无遮挡范围内看到警察 |
| 手电 | 初始60度、6格；对小偷连续有效照射0.8秒给1次标记；失去有效视线后清零 |
| 标记后的保护 | 第1、2次标记后1.5秒真隐身，再1秒不可重复标记；后1秒若被照亮可以显示身体；第3次立即失败 |
| 真隐身限制 | 所有照明都不能显示身体、携带物或名牌；可以移动，不能取件、交付、撤离 |
| 接触 | 两个角色不互相形成实体堵门；不设计触碰即抓捕 |
| 同步冲突 | 同一服务器逻辑步按“到时→第三次标记→撤离成功”顺序结算；只生成一个结果 |
| 交付提示 | 双方收到完成数量及粗略区域；不持续暴露小偷位置 |

“真隐身”和“黑暗中未被发现”是两种不同状态：前者即使进入光束仍不可见，后者进入有效光束就可见。用独立状态机管理，避免画面隐藏但服务器仍累计标记。

建议正常流程：房间准备→服务器开始→警察搜索/小偷取件→交付与追逐→标记触发保护或第三次失败→完成交付后撤离→结算→交换角色再来一局。断线、主动退出或后台挂起的首版策略是结束本局并记录“中断”，不发正常胜负；不承诺断线重连恢复。

### 两种道具的完整边界

- **宽光束**：警察手电短时变为90度、4格，持续3秒，冷却15秒。扩大搜索角度会牺牲距离，仍被墙和烟雾遮挡；不穿透真隐身。
- **烟雾**：小偷在当前位置制造约1.5格半径、持续3秒的烟区，冷却20秒；遮挡双方视觉与照明。烟区位置是公开线索，相当于暴露最后区域以换取离开机会。位置公开是明示的玩法代价，不是无意泄露隐藏坐标。
- 服务器决定是否可使用、何时结束、冷却是否完成；一条请求不能重复产生多个道具。先实现无遮挡、无道具的完整对局，再加道具。

### 地图建议

至少有两个环路、数个可绕行墙角和两个分离出口。将取送点分布在不同区域；避免唯一狭窄通道成为永久守点。地图加载时检查所有任务点和出口可达；试玩时检查角色初始位置、最短路线、交付站等待区是否产生必胜策略。概念图只说明视觉信息，不直接作为最终碰撞地图。

## 5 实现思路和范围控制

### 5.1 技术结构

1. `simulation`：普通Java，包含地图、玩家、任务、状态机、碰撞、可见性、胜负。不要依赖Android UI。
2. `core`：libGDX渲染、输入、音效、屏幕导航与网络观察状态。
3. `android`：Android启动、权限、生命周期、Room及振动等平台功能。
4. `server`：Java-WebSocket连接与房间管理，调用共享模拟逻辑；首版在笔记本运行。
5. 可选桌面客户端仅用于调试；最终必须用Android实机证明可用。

客户端发送操作，服务器计算结果。不能让客户端直接提交“我已经交付”“对方被我抓住”或任意坐标。输入包含序号、方向、朝向和动作；服务器检查重复、速度、角色权限及冷却。

先采用30Hz逻辑步、10–15Hz状态快照、客户端插值。它们是实验起点，最终频率由设备和网络数据决定。WebSocket较容易在Java两端搭建，但可靠有序传输在抖动时可能造成等待；LAN短局适合先验证，不能直接保证公网竞技体验。

### 5.2 可见性判定

对警察位置P、小偷位置T、朝向单位向量D，先检查距离，再检查方向夹角，最后对P到T做网格射线遮挡判断。目标若处于真隐身，则直接不可见。有效照射计时由服务器维护，不能由每台手机自己的帧率决定。

绘制光束也应使用同一份墙体数据和一致遮挡逻辑。否则会出现视觉上照到了、规则上没有照到的问题。优先测试墙角、光束边缘、紧贴墙、低帧率、大步长以及烟雾边缘。

### 5.3 隐藏信息与生命周期

每个客户端仅接收该角色应知道的内容。不应把完整对手坐标发给警察再简单隐藏图片。隐藏切换时立刻清空对手的插值缓存、血条/标记条附着物和携带物渲染；任务状态的精确变化也需要过滤。烟雾公开区域、交付粗略提示属于规则允许的信息。

网络回调只入队；游戏线程消费消息并更新渲染状态，避免跨线程访问渲染对象。[libGDX线程说明](https://libgdx.com/wiki/app/threading)

第一周验证两台真实手机、笔记本和实际教室网络；有些Wi-Fi隔离客户端，不能等演示当天才发现。首版支持输入服务器地址和房间码，二维码可以后续添加。根据选定target SDK核查LAN权限；Android官方文档区分Android 16过渡机制和Android 17面向新目标版本的本地网络权限要求。[Android本地网络权限](https://developer.android.com/privacy-and-security/local-network-permission)

房间码只用于定位对局，不等同于身份认证。课堂LAN原型应明确运行环境；若之后公开部署，再补传输加密、会话验证、限流等工作，不能沿用原型配置直接宣称安全上线。

### 5.4 分层范围

| 级别 | 功能 | 完成标准 |
|---|---|---|
| 必须完成 | 移动/碰撞、定向视野、标记与保护、三组取送、撤离/倒计时、双机联机、基本结果/历史、教程和设置 | 双手机能完整对局，规则一致，结果可保存 |
| 计划完成 | 宽光束、烟雾；交付区域提示；体验调优 | 道具对视野和状态产生正确影响，没有重复触发 |
| 有余力再做 | Bot训练、额外地图、诱饵脚步、更多局内统计 | 基础验收完成后再决定 |
| 本期不承诺 | 3D、多人组队、公网匹配、段位、账号、商店、地图编辑器、完整录像回放 | 避免挤压课程核心学习与可靠性 |

不建议把LLM API接入实时抓捕或胜负判断：它不能替代稳定、可重复的规则，且增加延迟和依赖。若以后做Bot，先用有限状态机与寻路，它也必须遵循同样的视野限制。

Room核查页面提供纯Java的annotationProcessor配置，不必为使用Room把整个项目换为Kotlin。首版可用Room 2.x路线，但依赖版本、最低系统版本、Gradle和JDK组合要在首轮构建中确认。本轮未做项目集成或APK构建，不将“有官方文档”当作兼容性测试通过。

没有找到前三款商业竞品在所核查官方入口提供的可复用游戏源码，因此不虚构“选中某款商业游戏源码进行二次开发”。选用libGDX作为技术基础符合新建项目并复用基础设施的路线；如果教师额外要求必须修改一款完整开源游戏，需要另行确认，而不是从exemplar推断这一限制。

建议维护`THIRD_PARTY_NOTICES`和资源清单，记录源码/素材网址、版本或commit、许可、用途、改动与负责人。实际复制某段示例代码时在附近注释其来源，并保留所需许可通知。竞品商店图仅用于本次比较展示，不作为游戏内可发布美术资源。

## 7 UI与用户流程

| 页面 | 必需内容 | 错误/空状态 |
|---|---|---|
| 首页 | 加入对局、玩法教程、历史、设置 | 无服务器也可查看教程和历史 |
| 连接与房间 | 地址、房间码、连接状态、角色占用、准备按钮 | 地址格式错误、房间不存在/已满、连接超时、角色被占用 |
| 教程 | 两种胜利条件；普通隐藏/真隐身/保护期区别；操作示例 | 简短分步说明，随时退出，不强制联网 |
| 警察对局 | 方向光束、准星、照射进度、标记数、交付总数、时间、宽光束冷却 | 掉线或服务器失联明确提示；旧对手图像不能残留 |
| 小偷对局 | 携带物、站点对应、交互进度、被标记/隐身剩余时间、烟雾冷却 | 无可交互目标时禁用动作并解释；不显示远处警察位置 |
| 结算 | 结果和原因、时长、任务数、标记数、事件时间线、换边再玩 | 中断局显示“中断”而非错误地判一方胜 |
| 历史与设置 | 按角色筛选、查看细节/删除；声音、振动、操作大小与灵敏度 | 首次使用显示空历史；删除需要清晰确认 |

画面采用深色地图、蓝色圆形警察、橙色菱形小偷；状态同时用文字/形状表达，不能仅靠颜色。菜单使用熟悉的Android导航和反馈。游戏里给触摸区留出安全边距，提供可调大小；音效事件也有视觉反馈。

核心对局概念图位于配套PPT第7页。它验证的是信息布局方向，尚未验证触摸舒适度、精确光照几何或最终关卡连通性。其他页面已有流程和状态说明，但不应声称已经完成全部可点击交互原型。

## 8 对应四个开发方面的证据

| 方面与文件01权重 | 本项目对应工作 | 可展示证据 |
|---|---|---|
| 输入20% | 多点触摸移动/瞄准/动作；地址/房间码；设置；网络输入 | 非法输入处理，触摸取消后角色停止，后台切换不持续移动 |
| 处理25% | 固定时间步、碰撞、视线、状态机、任务/胜负、角色信息过滤 | 规则测试、服务器日志和边缘情形演示 |
| 存储20% | Room战绩、事件时间线、设置；服务器内存里的活动对局 | 重启后查询、按角色筛选、删除；同局结果去重 |
| 输出与UI25% | 双方不同视野、进度/冷却、音效/振动、结果与历史 | 两机并排展示信息差、不同尺寸和可读性检查 |
| 整合10% | 操作经服务器处理到画面反馈及最终保存 | 完整对局演示、失败路径及个人技术解释 |

建议数据模型：`MatchResult(matchId, role, outcome, reason, duration, deliveredCount, markCount, finishedAt, rulesVersion)`；`MatchEvent(matchId, elapsedMs, eventType, publicZone)`。先存一局中少量关键事件，不存每个画面帧；活动对象也不频繁落库。以matchId确保结算重复到达不会插入两份战绩。

## 10 风险、验证与验收

| 风险 | 提前验证 | 接受条件/处理 |
|---|---|---|
| LAN不通或宿舍/教室Wi-Fi隔离 | 第一阶段两手机实测 | 明确可用网络方案；地址和权限失败有反馈 |
| 看起来照到却没有判定，或穿墙判定 | 固定墙角/角度/距离测试场景 | 渲染与规则使用同一地图；所有列出的边缘场景解释一致 |
| 隐身后还会被持续标记 | 状态进入/退出和边界时刻测试 | 真隐身0累计；保护结束前不重复计数；第3次立即结算 |
| 隐藏坐标通过网络/物品变化泄露 | 检查各角色快照、事件和客户端缓存 | 未知位置不发送；公开烟区和交付区域属于明示线索 |
| 双端不同胜负或重复交付 | 同步操作、重发、同一逻辑步冲突测试 | 服务器只产出1次结果；动作幂等或去重 |
| 挂后台、退出、掉线 | 真机切换应用、关闭连接 | 清除持续输入；中断提示，无崩溃；不伪造正常胜负 |
| 明显守点必胜/某角色过强 | 若干玩家20–30局交替角色 | 报告样本、经验差异、地图/角色胜率与原因；仅作探索，不宣称统计公平 |
| 存储无实际用途或丢数据 | 完局后重启、筛选、清空 | 战绩能查看和删除，重复消息不重复记录；不保存不必要个人信息 |
| 功能太多 | 每周审查剩余任务与人时 | 第12周冻结；缺时间先削扩展，不重写核心方向 |

性能目标需在具体设备上测量：记录帧时间分布、实际快照频率、操作到可见反馈的延迟和网络条件。60fps是期望体验，不是本次已达到的结果。局域网方案也不是公网部署验证。

阶段学习记录建议用“遇到的问题→尝试→证据→学到的内容→下一步”结构。Alpha重点是Java模块和规则；Beta重点是Android生命周期、网络与数据库整合；Final解释性能、平衡取舍和未完成项。AI可帮助查文档、原型和测试，但成员必须能说明保留下来的代码。
