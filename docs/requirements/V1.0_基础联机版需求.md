# Light Chase V1.0 基础联机版开发需求

版本：V1.0（基础联机版）  
文档日期：2026-10-23；修订：R1  
状态：用户本轮已确认沿用基础玩法，新增实现参数为建议；尚未实现或验收  
开发团队：沿用模板的 3 人；单局 2 人，警察与小偷各 1 人。

## 1. 文档依据与适用范围

本版目标是让两台 Android 手机通过局域网完成一局基础对抗，不加入钥匙、新区域、主动道具或传感器玩法。版本方向依据 2026-10-23 本次沟通；具体玩法数值和 F01–F13、A01–A22 继承用户提供的模板，便于开发及验收追踪。

本文件第 2–15 节保留模板正文。其中“已确认”“明确确认”“原项目说明”等表述均是模板的历史措辞，表示本次继承的玩法基线，不表示本次用户逐项重新确认，也不意味着已查验原说明或已完成实现。第 12 节仍为建议实现约定和待设计事项；采用时需记录具体决定。

用户本次指令优先于模板内的阶段性说明。当前基础玩法与技术方案已确认，按第 16 节及开发设计的里程碑实施。未来功能尚未选择，地图解锁和传感器只是举例；这里只落实必要的结构准备。

相关文件：[版本规划](README.md)、[跨版本扩展约定](跨版本扩展约定.md)、[输入快照](reference/Light_Chase_第一版开发需求文档_输入快照.md)。

## 2. 第一版目标与功能边界

### 2.1 目标

实现一局可以由两台 Android 真机完成的联机对抗：进入房间、选择角色、准备开局、移动搜索、拾取与运送物资、照明标记、撤离或抓捕、胜负结算。

第一版优先保证规则完整、双方状态一致、角色信息显示正确。画面可以使用简单的几何图形、颜色和文字标识，不以精细美术作为验收前提。

### 2.2 本版包含

| 编号 | 功能 | 范围 |
|---|---|---|
| F01 | 局域网联机 | 两台 Android 手机连接电脑上的 Java 服务器 |
| F02 | 房间与开局 | 输入 IP、房间号，选择角色，双方准备，3 秒倒计时 |
| F03 | 固定地图 | 约 24×18 格，墙壁、绕行路线、固定出生点、任务点及出口 |
| F04 | 角色移动 | 左侧虚拟摇杆、等速移动、墙壁碰撞、警察朝向跟随移动 |
| F05 | 主视窗 | 镜头跟随自己，统一 16:9 游戏范围，约 14.2×8 格 |
| F06 | 角色可见性 | 小偷在矩形视窗内隔墙观察警察；警察通过手电筒发现小偷 |
| F07 | 手电筒与标记 | 60°、4 格，连续照射 0.8 秒标记一次，三次抓捕 |
| F08 | 隐身与免疫 | 前两次标记后隐身 1.5 秒，再免疫 1 秒 |
| F09 | 物资任务 | 三组一一对应任务、单件携带、拾取、交付、主动丢弃 |
| F10 | 出口与胜负 | 三次交付后开放两个出口，180 秒时限，统一结局优先级 |
| F11 | 对局界面与小地图 | 时间、标记数、交付数、角色状态、受权限限制的地图信息 |
| F12 | 对局异常处理 | 退出、切后台、掉线判负；无断线重连 |
| F13 | 本局结算 | 显示胜方、结束原因及本局基本数据 |

### 2.3 本版不包含

- 烟雾弹、强化光束以及其他道具或技能。
- AI 对手、单机模式、同设备双人模式。
- 多张地图、随机地图、随机出生点或随机任务点。
- 账号、登录、互联网匹配、云服务器部署、自动发现服务器。
- 断线重连、后台继续对战、暂停后恢复对局。
- Room/SQLite 战绩数据库、历史记录、事件回放、排行榜。
- 独立教学系统、复杂设置、音效和振动系统、精细角色动画。

以上排除项只限定第一版，不代表从最终项目中永久删除。

## 3. 使用环境与总体流程

### 3.1 环境

- 开发语言和工具沿用 Java、Android Studio，游戏框架沿用 libGDX。
- 电脑运行 Java 服务器；两台手机连接同一 Wi-Fi 或热点，并可访问该电脑。
- 网络传输沿用 WebSocket 方向；第一版不引入本地战绩数据库。
- 服务器由组员手动启动，手机手动填写服务器 IP 和房间号。
- 游戏横屏运行；两个客户端分别使用警察和小偷角色。

### 3.2 正常对局流程

1. 组员在电脑上启动服务器。
2. 两名玩家在手机上输入服务器 IP 和相同房间号。
3. 两人选择不同角色，分别点击准备。
4. 双方准备完成后进行 3 秒开局倒计时。
5. 对局开始，两名角色和三个物资出现在固定起始位置，180 秒计时开始。
6. 警察移动并通过手电筒寻找、标记小偷。
7. 小偷自行选择顺序，将三个物资分别送到对应交付点。
8. 三次交付全部完成后，两个出口同时开放。
9. 服务器根据超时、第三次标记或成功撤离确定胜负；退出、切后台、掉线也可提前结束比赛。
10. 客户端显示本局结算。

## 4. 地图、坐标与移动规则

### 4.1 地图内容（F03）

- 一张约 24 列×18 行的固定网格地图。
- 至少包含两条可绕行的环路，提供搜索、躲避和路线选择空间。
- 警察和小偷各有一个固定出生点。
- 三个固定物资起始点，编号 M1、M2、M3。
- 三个固定交付点，编号 D1、D2、D3，分别与 M1、M2、M3 对应。
- 两个固定出口 E1、E2。
- 每局地图布局、出生点、物资起始点、交付点和出口位置均不变化。
- 固定点位必须可达；物资、交付点和出口应能明确区分。
- 具体墙体坐标和点位坐标由后续地图设计给出，本文件不将概念图当作最终地图。

### 4.2 距离与移动（F04）

“1 格”作为游戏世界的统一距离单位。涉及拾取和视线判定的距离，均以世界坐标中的角色或目标中心计算，而不是手机物理像素。

| 项目 | 规则 |
|---|---|
| 基础速度 | 警察、小偷均为每秒 3 格 |
| 斜向移动 | 归一化移动方向，不因同时沿两个轴移动而加速 |
| 携带物资 | 不降低速度 |
| 墙壁及边界 | 阻挡移动，角色不能穿墙或离开可走区域 |
| 角色之间 | 不产生身体阻挡，可以相互穿过 |
| 操作 | 两个角色均由左侧虚拟摇杆控制移动 |
| 警察照射方向 | 自动跟随移动方向；停止后保持最后一次移动方向 |

## 5. 镜头、角色可见性与小地图

### 5.1 主视窗（F05）

- 镜头跟随本地玩家，角色位于游戏视窗中心。
- 以 16:9 横屏为统一参考，显示宽约 14.2 格、高 8 格的矩形区域；精确宽度为 8×16÷9 格。
- 不同手机使用等比例适配与留边，保持相同的世界显示范围，不因屏幕更宽而获得更大观察范围。
- 视窗内地形正常显示，墙壁不会把其后地形遮黑；不实现探索迷雾或地形记忆。
- 手电筒只决定警察是否能发现和标记小偷，不决定地形是否显示。
- 普通对象是否显示，还要遵守下述角色和物资权限，不能仅因进入镜头就显示全部对象。

### 5.2 对手角色的可见规则（F06）

| 观察方 | 对手何时可见 | 墙壁影响 |
|---|---|---|
| 小偷观察警察 | 警察中心进入以小偷为中心的统一矩形视窗范围 | 不受墙壁遮挡 |
| 警察观察小偷 | 小偷位于有效手电筒范围内，且不处于真正隐身状态 | 墙壁阻挡光线，不能隔墙发现 |

补充说明：

- 小偷原先“半径 4 格”的观察规则已被矩形视窗规则替代，不能同时保留两套规则。
- 警察即使与小偷在同一主视窗内，也不能直接看到未被有效照亮的小偷。
- 小偷在 1.5 秒真正隐身期间，警察看不到其角色和携带物资。
- 随后的 1 秒免疫期间，警察可以在有效光照下看到小偷，但不能对其累计标记进度。
- 对手在主画面和小地图中的可见性应保持一致，不能通过小地图绕过角色视野规则。

### 5.3 小地图与物资显示（F11）

双方小地图均显示完整地图布局、自己位置、三个物资起始点、对应交付点及两个出口。出口是否开放应有状态区分。

| 信息 | 警察 | 小偷 |
|---|---|---|
| 地图、固定任务点、出口 | 可见 | 可见 |
| 自己位置 | 可见 | 可见 |
| 对手位置 | 仅满足警察角色可见条件时显示 | 仅在自己的矩形观察范围内显示 |
| 起始物资是否已被拿走 | 可见 | 可见 |
| 丢在其他位置的物资 | 主画面、小地图均不可见 | 小地图显示所有地上物资实际位置，主画面显示镜头内物资 |
| 携带物资的位置 | 不提供可独立追踪的位置标记 | 显示本人携带状态 |
| 已完成交付数量 | 显示总数 | 显示总数，并可区分自己的任务状态 |

警察只获得交付总数，不获得交付区域、具体交付点完成情况或额外的搬运轨迹提示。固定交付点图标的状态不能反过来泄露每次交付发生的位置。

## 6. 手电筒、标记与保护状态

### 6.1 手电筒（F07）

| 参数 | 第一版数值 |
|---|---|
| 开关状态 | 始终开启，不提供开关按钮 |
| 扇形总角度 | 60°，朝向两侧各 30° |
| 最远射程 | 4 格，替代原说明中的 6 格 |
| 射程依据 | 统一游戏视窗短边的一半；向上或向下时最远到视窗边缘 |
| 朝向控制 | 警察移动方向，停止后保持 |
| 遮挡 | 墙壁阻挡，不能穿墙照明或标记 |

4 格是世界距离，不能因设备分辨率或物理屏幕宽度变化而变化。光束可以按实际无遮挡区域绘制，但视觉效果与服务器有效照射范围必须一致。

### 6.2 有效照射与标记（F07）

服务器同时检查距离、扇形角度、墙体遮挡和小偷状态：

1. 小偷处于 4 格射程内。
2. 小偷位于手电筒朝向两侧各 30° 范围内。
3. 警察到小偷的视线不被墙壁阻挡。
4. 小偷不处于真正隐身或免疫保护期间。

上述条件连续保持 0.8 秒，累计标记次数加 1。未满 0.8 秒时，任一条件中断，本次照射累计清零；已经完成的标记次数不会因逃离光照而减少。

第三次标记立即触发小偷失败。一次完成的标记不能在同一判定时刻重复累计。

### 6.3 标记后的状态（F08）

前两次标记后的状态顺序：

`普通状态 → 被标记 → 真正隐身 1.5 秒 → 免疫保护 1 秒 → 普通状态`

| 行为或效果 | 普通状态 | 真正隐身 1.5 秒 | 随后免疫 1 秒 |
|---|---|---|---|
| 移动 | 允许 | 允许 | 允许 |
| 被警察看见 | 满足有效光照时 | 不可见 | 满足有效光照时 |
| 累计标记进度 | 可以 | 不可以 | 不可以 |
| 拾取、交付、撤离 | 允许 | 禁止 | 允许 |
| 主动丢弃物资 | 允许 | **允许** | 允许 |
| 原有携带物资 | 保留 | 保留，向警察隐藏 | 保留 |

真正隐身期间允许丢弃是本版明确确认的例外，不能被“隐身禁止交互”的统一判断拦截。保护结束后，下一次有效标记必须重新连续照射满 0.8 秒。

## 7. 物资任务与交互

### 7.1 任务与携带（F09）

- 全局只有 M1、M2、M3 三个物资，各自身份在拾取、丢弃、重新拾取后保持不变。
- 小偷可自行选择完成顺序。
- 每次最多携带一个物资，携带期间不能拾取第二个物资。
- M1 只能交付到 D1，M2 只能交付到 D2，M3 只能交付到 D3。
- 在错误交付点不能完成交付，不能消耗物资或增加交付计数。
- 每个物资只能成功交付一次，计数最多为 3。
- 前两次被标记不会自动掉落物资，也不会回退已完成的交付。
- 警察不能拾取、携带、丢弃或交付物资。

单个物资的基本状态：

`起始点地面物资 → 携带中 → 已交付`

携带中也可以转为 `丢弃在地面 → 再次携带中`，不新增物资副本。

### 7.2 按住交互（F09、F10）

拾取、交付和撤离统一采用以下条件：

- 角色中心与目标中心的直线距离不超过 0.8 格。
- 角色到目标之间没有墙壁，不允许隔墙拾取、交付或撤离。
- 小偷处于允许操作的状态，目标也满足操作条件。
- 按住右侧交互按钮并保持静止，连续 1 秒完成。
- 松开按钮、移动、被标记或目标失效时，立即取消并清空本次进度。
- 真正隐身期间不启动这些操作；免疫保护期间允许操作。
- 多个可拾取物资重叠时，优先最近的物资；同距离时按物资编号选择。

客户端应显示当前可操作目标、操作类型和进度；没有有效目标时，交互按钮应呈现不可操作状态。

### 7.3 主动丢弃（F09）

- 携带物资时显示独立“丢弃”按钮。
- 点击后立即将携带物资放在角色脚下，不需要等待 1 秒。
- 真正隐身和免疫期间均可丢弃。
- 丢弃后角色恢复空手，物资编号、对应交付点和已完成交付数量不改变。
- 地面物资只有小偷能够重新拾取，仍需满足 0.8 格、无遮挡和按住 1 秒条件。
- 警察看不到被丢弃的地面物资，不能因此获得隐身小偷的位置。

## 8. 出口、时间与胜负

### 8.1 出口（F10）

- 三个物资全部交付前，两个出口均关闭；接近出口不能提前完成撤离。
- 第三个物资成功交付后，两个出口同时开放。
- 小偷可任选一个开放出口，在 0.8 格内、无遮挡且保持静止时按住交互按钮 1 秒。
- 完成撤离即小偷获胜；撤离过程同样可因松手、移动或被标记而取消。

### 8.2 比赛时间与结局（F10、F12）

| 触发条件 | 结果 |
|---|---|
| 剩余时间到 0，且此前未结算 | 警察获胜 |
| 小偷累计第三次被标记 | 警察获胜 |
| 小偷完成三个交付，并成功撤离 | 小偷获胜 |
| 任意一方在对局中主动退出 | 退出方失败，另一方获胜 |
| 任意一方在对局中切到后台 | 切后台的一方失败，另一方获胜 |
| 任意一方在对局中被确认掉线 | 掉线方失败，另一方获胜 |

单局时间为 180 秒，从开局倒计时结束、角色可以行动时开始计算。三秒开局倒计时不占用比赛时间。

在同一服务器判定时刻，同时满足多个正常玩法结束条件时，按以下优先级结算：

`超时 > 第三次标记 > 撤离成功`

客户端本地计时、画面先后或按钮反馈不作为胜负依据。服务器一旦完成结算，不再接受后续操作改变结果。

## 9. 房间、界面与异常流程

### 9.1 连接与大厅（F01、F02）

- 连接页面提供服务器 IP、房间号和连接操作。
- 大厅显示房间号、连接状态、警察与小偷两个角色槽、双方准备状态。
- 同一房间最多两名玩家，同一角色只能由一人占用。
- 两人选择不同角色并都准备完成，才能进行 3 秒倒计时。
- 倒计时结束前不能移动、拾取、丢弃、照射累计或进行其他对局操作。
- IP 或房间号为空、连接失败、房间已满、角色已被占用时，应给出明确提示。
- 双方只要使用同一个可用服务器和房间号，就应能进入同一房间，无需账号。

### 9.2 对局界面（F11）

| 区域 | 警察 | 小偷 |
|---|---|---|
| 主画面 | 自己、地形、固定点位及按权限可见的对象 | 自己、地形、固定点位及按权限可见的对象 |
| 左侧 | 移动摇杆 | 移动摇杆 |
| 右侧 | 不提供独立瞄准摇杆、交互或道具按钮 | 按住交互按钮；携带时另有丢弃按钮 |
| 双方共有信息 | 剩余时间、累计标记次数、交付数量 | 剩余时间、累计标记次数、交付数量 |
| 小偷额外信息 | 不显示小偷私有状态面板 | 携带编号、交互目标及进度、隐身或免疫剩余时间 |
| 小地图 | 按第 5 节权限显示 | 按第 5 节权限显示 |

重要反馈至少通过文字、数字、进度或图形明确表达，不以音效或振动作为唯一信息来源。

### 9.3 结算页面（F13）

显示胜方、本人的胜负、结束原因、已交付数量、累计标记次数及本局用时。只展示本局结果，不要求退出应用后保留数据。

### 9.4 退出、后台与掉线（F12）

- 对局中主动退出、切后台或被确认掉线，均判该玩家失败。
- 切到后台时立即停止持续移动和持续交互输入，并终止该玩家继续参与本局。
- 掉线由服务器检测，最多等待 5 秒确认；确认后结算，无需等满剩余比赛时间。
- 不实现断线重连；恢复网络或回到前台不能继续已结束的比赛。
- 未开局时的离开不记为对局失败，不得让一名玩家独自开始比赛。
- 服务器不可达时，客户端应显示连接或中断原因，不自行伪造一个已被服务器确认的胜负。

## 10. 联机一致性与信息权限

本节沿用原项目的服务器统一判定方向，不规定具体类名或目录结构。

### 10.1 服务器负责

- 房间、角色占用、准备和对局状态。
- 角色合法位置、碰撞和朝向。
- 手电筒命中条件、连续照射进度、标记次数。
- 隐身、免疫、交互进度及比赛时间。
- 物资状态、携带关系、交付数量和出口状态。
- 角色可见性、发往各客户端的信息过滤。
- 唯一的比赛结局和离开、掉线判负。

### 10.2 客户端负责

- 采集移动、准备、交互、丢弃和退出等操作请求。
- 渲染服务器认可的游戏状态，显示状态和错误提示。
- 进行必要的画面平滑，不能自行决定拾取成功、标记成功或胜负。
- 在应用切后台、断开或结算后及时清空持续输入。

### 10.3 必须保持的一致性

- 客户端不能通过直接上报坐标、交付数或胜负改变权威状态。
- 重复交互请求不能复制物资、重复交付或增加标记次数。
- 隐藏对手时应在服务器发送前过滤其坐标和形象，不能只在界面上隐藏图形。
- 发往警察的数据不得包含可追踪丢弃物资的位置，也不得借携带物资坐标泄露隐藏的小偷。
- 视觉光束、服务器照射判定和小地图对手标记必须使用一致的有效范围。

## 12. 建议实现约定与待设计事项

本节用于给开发者提供起点，不与已确认玩法混写。若建议影响范围或规则，应先更新本需求文档。

### 12.1 建议实现约定

| 事项 | 建议默认方案 | 说明 |
|---|---|---|
| 空房间创建 | 首位玩家输入尚不存在的房间号时自动建房 | 不新增单独的建房系统 |
| 准备状态变化 | 更换角色或有玩家离开时，取消准备和开局倒计时 | 防止角色变化后误开局 |
| 结算后去向 | 提供返回大厅入口；新局重新准备 | 不要求自动交换角色或一键重赛 |
| 警察初始朝向 | 朝地图内部，写入固定地图配置 | 第一帧就有确定朝向 |
| 镜头靠近地图边缘 | 角色仍位于视窗中心，地图外显示背景 | 不扩大可见世界范围 |
| 射线判定对象 | 以角色中心作为距离、角度和遮挡判定点，边界包含在有效范围内 | 避免客户端和服务器使用不同几何规则 |
| 同帧交互与标记 | 先处理标记对交互的中断，再提交仍有效的交互 | 第三次标记和撤离仍服从已确认结局优先级 |
| 移动输入与交互 | 收到非零有效移动输入即取消交互，包括被墙挡住的移动尝试 | 避免靠墙推动摇杆仍完成操作 |
| 按住按钮跨目标 | 不自动把已累计进度转移到另一个目标，目标变化后重新开始 | 避免重叠物资导致错误拾取 |
| 丢弃与按住交互并发 | 丢弃取消当前交互；需要重新按下才能拾回刚丢弃的物资 | 避免立即自动捡回 |
| 起始物资状态 | 警察显示“原始物资是否已被取走”，丢回起始点不提供额外位置提示 | 避免通过物资落点泄露位置 |
| 掉线等待期间 | 清空失联玩家输入，不暂停总计时，正常结局若先发生则先结算 | 5 秒是失联确认上限，不是无敌或暂停时间 |
| 结束事件冲突 | 服务器按既定规则只提交一次结局，结束后到达的离开事件不改判 | 避免退出操作覆盖已完成结局 |
| 双方失联或服务器故障 | 无法得到权威胜负时显示连接中断；不由客户端猜测胜方 | 单方明确离开时仍按已确认规则判负 |
| 更新频率 | 暂沿用原说明的服务器 30 Hz 模拟、10–15 Hz 状态广播，并作画面插值 | 作为实现起点，不额外扩展玩法 |

### 16.2 为下一版保留的结构

采用《跨版本扩展约定》X01–X08：地图和参数集中管理；物资、任务点及出口使用稳定 ID；触摸输入转换为动作请求；服务器完整状态与角色可见快照分离；协议/地图版本检查；单一结局入口；新局完整重置。

首版不实现钥匙背包、门锁状态、额外地图或传感器采样。固定地图全部可达，三个物资对应三个交付点，两个出口保持原有开放条件。预留结构不得引入新的玩家操作或改变视野规则。

### 16.3 建议采用的完整对局收尾

模板第 12 节的“结算后返回大厅并重新准备”作为本次建议验收目标：正常结算后能返回大厅；服务器可用且连接正常时再次准备开始新局，新局状态完全重置。连接已中断的一方回到连接页，不能恢复旧局；重新建立连接后可参与新局。服务器故障不能由客户端自行决定胜方。

这一补充让基础联机演示可以连续进行，不要求账号、历史战绩或自动交换角色。
