# Light Chase 跨版本扩展约定

日期：2026-10-23　状态：实现建议；服务于 V1.0，不新增首版玩法

修订 R2：后续功能尚未选择。下表的钥匙、区域和传感器只说明结构可能怎样扩展，不代表 V2/V3 排期。规则和角色视图由游戏逻辑负责人实现；联网负责人负责调用与投递，客户端负责人负责输入与呈现。详细边界以 [开发文档](../development/01_分工与开发设计.md) 为准。

## 1. 原则

V1.0 只实现当前使用的能力。预留空间意味着减少地图、任务和输入之间的硬编码依赖，不意味着提前编写地图编辑器、插件系统、通用脚本引擎或传感器框架。

## 2. V1.0 必须落实的最小准备

| 编号 | 准备 | V1.0 如何落地 | 后续如何扩展 |
|---|---|---|---|
| X01 | 地图数据与规则分离 | 一份地图定义保存地图 ID、版本、宽高、墙体、出生点、物资点、交付点和出口；运行中读取，不在渲染层散落坐标 | 若日后选择区域玩法，可新增地图数据而不重写基础移动算法 |
| X02 | 稳定实体 ID | 物资、任务点、出口分别有唯一 ID；任务明确绑定物资和交付点 | 增加钥匙/解锁目标，不把物资数量写进每个界面和网络处理函数 |
| X03 | 配置与运行状态分离 | 速度、光束、保护时间等集中配置；本局状态独立保存；首版仍固定三组任务和两个出口 | 后续调整地图或配置时可追溯，不需要修改多个客户端常量 |
| X04 | 统一操作入口 | 摇杆和按钮生成移动、交互、丢弃等语义请求，游戏逻辑不直接读取 UI 控件 | 若日后选择新的输入方式，可转换为经批准的动作，触控仍能复用 |
| X05 | 权威状态与角色视图分离 | 服务端维护完整状态，分别生成警察/小偷允许看到的快照；隐藏物资和角色在发送前过滤 | 区域与钥匙加入后延续同一过滤过程，防止新增字段泄露位置 |
| X06 | 协议兼容检查 | 连接握手包含协议版本和地图版本；不兼容时拒绝开始并提示更新；消息有类型，对动作可进行去重 | 未来有破坏性协议变更时升级版本，首版不要求同时支持多套协议 |
| X07 | 单一结局入口 | 规则事件统一提交给结局判定，结算幂等，结束后停止动作提交 | 解锁、传感器事件不能绕过胜负优先级或结束状态 |
| X08 | 新局完整重置 | 初始化由配置生成，不从上一局残留状态复制；基础状态有明确生命周期 | 新增门、钥匙或传感器状态时统一纳入重置 |

配置化不改变首版规则：首版任务总数必须是 3，出口数必须是 2，所有区域开局可进入。不能以“可扩展”为由让 V1.0 默认出现随机地图、可选规则或新的设置页面。

## 3. 建议模块边界

- 游戏规则：位置、碰撞、照明、标记、保护、物资和结局。尽量可脱离 Android 界面验证。
- 服务端：房间、连接、权威模拟、输入校验、角色视图和状态广播。
- Android 客户端：触摸输入、渲染、界面、网络接入与生命周期。
- 地图与参数：静态数据及校验；不保存本局玩家状态。

这是职责划分，不指定成员、不要求固定类名，也不强制建立复杂的多层框架。服务器应使用自己的时间和可信位置判定事件；客户端不能提交“已解锁”“已标记”或“获胜”来更改结果。

## 4. 留到后续版本实现

后续新功能必须单独立项，经过玩法选择与验收定义后再实现；不预定地图、钥匙或传感器功能。V1.0 不需要发送这些示例功能的空字段，不申请未使用的权限，也不增加无功能按钮。

## 5. 结构验收

| 编号 | 通过标准 |
|---|---|
| XA01 | 修改开发地图中的一个任务点坐标后，服务端判定、主画面和小地图都使用同一数据；不需逐处修改常量 |
| XA02 | 新一局恢复原始物资、计时、位置和保护状态；不继承上局结果 |
| XA03 | 开发日志或测试抓包中，警察快照不含隐藏小偷和丢弃物资位置；UI 隐藏不是唯一保护 |
| XA04 | 协议或地图版本不匹配时不能进入对局，双方能看到可理解的原因 |
| XA05 | 输入入口可在规则测试中提交语义动作，不依赖真实 UI；不要求用传感器实现此验证 |

上述检查补充基础玩法验收，不替代 A01–A22。协议字段、线程模型和精确目录结构在工程设计时再定。
