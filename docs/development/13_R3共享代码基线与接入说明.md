# R3 共享代码基线与接入说明

日期：2026-11-16。状态：共享类型、严格编解码器、固定测试配置及验证已经落地；运行端、规则引擎和 UI 尚未接入 v2，J0 尚未整体验收。

## 1. 当前可直接使用的代码

| 入口 | 用途 |
|---|---|
| `contracts/src/main/java/com/lightchase/contracts/v2/` | 三人唯一共用的 R3 类型与接口，共 41 个源文件；含输入、动作、回执、视图、卡、通道、光球、地图与配置 |

| [fixtures/v2](fixtures/v2/README.md) | 15 个完整消息包络及一份场景期望清单；已由真实 v2 Codec 测试读取 |

R3 类型放在统一的 `com.lightchase.contracts.v2` 包中，替代接口文档最初使用的未版本化包名。所有成员引用这同一个包，不复制 DTO。未变化的 `Role`、`Protection`、`MatchInit`、`MatchResult`、`RoomState` 等仍复用原 contracts 类型。

新类型使用 Java 17 record：读取字段用 `view.inventory()`、`frame.aimRad()`，不使用原 DTO 的直接字段访问。所有集合做防御复制，不可修改；两个道具槽允许元素为 null。协议 JSON 字段名称不因 record 改变。Android Debug 构建已验证可打包，尚未在设备上验证新增功能。

## 2. 当前版本边界

现有正式运行入口仍使用 v1 引擎、网关、Codec 和资源，`com.lightchase.contracts.Protocol.VERSION` 仍为 1。新目标版本为 `com.lightchase.contracts.v2.Protocol.VERSION=2`。V2WireCodec 拒绝 v1 包，现有服务端尚不接受 v2 玩法包。

这是同一工程中的迁移阶段，不是同时提供两套在线玩法。不要单改现有 VERSION、替换旧 Codec 或提前换默认地图，避免握手通过后运行旧规则。A/B/C 对接完成、角色权限及整局通过后，再统一切换运行入口和资源哈希；新端不能静默降级到旧局。

本轮没有修改已有引擎、WebSocketClientGateway、AndroidLauncher 或 UI 调用点来冒充完成接入。共享接口已经可编译；成员仍需实现对应的新接口及替身，不能将此阶段直接标为新功能联机可玩。

## 3. 每个人的下一项具体任务

### A：规则引擎

在原 game-core 中新增实现 `com.lightchase.contracts.v2.MatchEngineFactory/MatchEngine` 的 R3 入口，使用 V2DataFiles 提供的地图/参数。先落实独立瞄准和双槽：固定 tick，输入 `StepInput`，返回 `StepResult`、两角色 `PlayerView`。不要把 v2 视图强行转换成旧视图导致字段丢失。旧基础规则可以在内部复用，网络不能直接接触内部状态。

按 02 第 13.8 节处理动作、移动、照射和交互顺序，再逐项加入护盾、卡和传送。A 需要提供确定的动作序列及结果，B 先用假引擎、C 先用共享样例，不等待 A 全部完成。

### B：服务器与网关

以 V2WireCodec 为共享收发入口，实现 v2.ClientGateway 的 useItem 和 v2.GatewayListener 的 onAction；再接 USE_ITEM 入队、actionId 去重、结果关联及超时。Codec 只验证结构、方向和模型约束，不执行道具、解锁或传送规则。

调用 `codec.body(message, PlayerView.class)` 取得不可变 v2 视图。运行会话仍需校验 matchId、seq、tick、身份和阶段；不能因为通过 Codec 就认为玩家有权执行操作。先假引擎＋两个 JVM 客户端验证，再接 A 的新引擎。仅在集成通过后统一切换协议/资源版本。

### C：客户端

按 v2.ClientGateway/Listener 开发新输入与页面适配，建立脚本化假网关输出共享样例，捕获提交输入和 useItem。该替身不重写真实游戏规则，也不需要先完成 WebSocket。

首先验证左移动/右瞄准及顶层 `PlayerView.interaction()`；再做两槽、卡槽、通道、光球及右上角小地图。原始传感器值只留在本地，最终输出 `aimRad`。UI 不自行判定拾取或使用成功。真实网关由 B 在 App 注入，client-core 不另写网络协议。
