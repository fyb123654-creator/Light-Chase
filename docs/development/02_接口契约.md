# Light Chase 接口契约（R3 / 协议 v2）

> 2026-11-16：用户已确认全部十一项规则及独立瞄准/校准约定。本页是唯一正式接口定义；第 13 节完整定义 R3 的替换类型、新消息及规则时序，前文相应条目引用该节。未变更的房间、心跳、结算、线程与严格校验沿用原约定。

目标契约 `protocolVersion=2`；文档修订 R3，日期 2026-11-16。**共享 v2 类型、Codec 和配置已落地并验证；运行端仍为 v1，规则/网关/UI 尚未接入。**代码入口与分阶段迁移见 [13 共享代码基线](13_R3共享代码基线与接入说明.md)。协议版本常量必须和完整实现一起升级，不能只改常量宣称支持 v2。

## 1. 统一类型与约束

- string 为 UTF-8，ID 大小写敏感，服务器生成 sessionId/playerId/matchId/resultId，客户端不得选择或伪造 playerId。房间号按开发设计规范化。
- int 为有符号 32 位整数；long 在 JSON 中使用非负整数且不超过 2^53−1；float/double 必须有限，拒绝 NaN/Infinity。位置与角度用 double，传输不要求小数位固定。
- Role=`POLICE|THIEF`；RoomPhase=`LOBBY|COUNTDOWN|RUNNING|FINISHED`；Protection=`NORMAL|INVISIBLE|IMMUNE`；InteractionType 以第 13.1 节的完整枚举为准。
- Position=`{x:double,y:double}`；Pose=`{x:double,y:double,headingRad:double}`。坐标单位和方向见开发设计。这是接口描述用的概念记法，代码中对应 `MapPoint`、`SpawnPose`、`ActorPose`，基础命名对应 contracts；R3 替换类型的目标字段以第 13 节为准，源码待迁移。
- 下文 `T?` 表示字段必须存在但允许 null，`[T]` 表示数组可为空；没有 `?` 的字段必填且不得 null。只有明确写“禁止出现”的角色私有字段才完全省略。未经版本升级的未知字段、枚举、消息类型均拒绝，避免静默误解。
- 所有模型使用普通不可变 DTO 或构造后不修改的副本；禁止将引擎内部集合引用交给客户端或网络线程。

## 2. 进程内 Java 契约

以下为接口设计签名；DTO 的字段在后文定义。客户端不依赖内部 MatchState。

```java
public interface MatchEngineFactory {
    MatchEngine create(MapDefinition map, RuleConfig config, MatchInit init);
}
public interface MatchEngine {
    StepResult step(StepInput input);
    PlayerView viewFor(String playerId);
    MatchResult result(); // ACTIVE 时 null，结束后固定值
    MatchResult abort();  // 服务端无法继续时；未结束则SERVER_ABORTED，否则返回既有结果
}
public interface ClientGateway {
    void connect(ConnectionOptions options, GatewayListener listener);
    void selectRole(Role role);
    void setReady(boolean ready);
    void submitInput(InputFrame frame);
    void useItem(int slot, String expectedItemId); // R3 新增，见 13.2
    void returnToLobby();
    void leaveRoom();
    void background();
    void close();
}
public interface GatewayListener {
    void onSession(SessionInfo session); // null 表示身份失效
    void onControl(ControlStatus status);
    void onConnection(ConnectionStatus status);
    void onRoom(RoomState state);
    void onView(PlayerView view);
    void onResult(MatchResult result);
    void onError(GatewayError error);
    void onAction(ActionStatus status); // R3 新增，见 13.2
}
```

`MapDefinition`、`RuleConfig` 的字段定义在 [开发设计](01_分工与开发设计.md) 第 8 节（地图与配置交付），`RoomState`、`PlayerView`、`MatchResult` 在本文件第 6–8 节。本节只锁定接口签名，不重复字段表，避免两处各写一份。

所有客户端方法非阻塞；错误走 onError，不用异常穿过渲染线程。connect 正在连接或已连接时重复调用返回本地 ALREADY_CONNECTED，不偷偷创建第二个会话。close 幂等，清空缓存和输入；正在对局的用户主动离开须先调用 leaveRoom/background 表明原因，close 仅清理资源。

GatewayListener 回调由网关串行触发，可能发生在网络/定时线程，也可能同步发生在调用方法的线程；C 必须统一入队到渲染线程，不在回调中阻塞或重入调用网关。C 持续每帧更新 InputFrame，B 负责 20Hz 发送、边沿即时发送、心跳、序号、包络和自动 RESULT_ACK。C 不自己构造 JSON、计算 inputSeq 或处理 socket 断线。

若ClientGateway连续250ms未收到新的submitInput调用，应发送零向量与interactHeld=false，并清掉待发送drop脉冲；即使网络线程仍在运行，也不能无限重发渲染卡住前的操作。输入采样刷新和网络心跳是两个不同租约。

| 类型 | 完整字段/语义 |
|---|---|
| ConnectionOptions | host:string, port:int, roomId:string, clientBuild:string, mapHash:string, configHash:string。protocolVersion 由编译契约常量设置 |
| ConnectionStatus | state:`DISCONNECTED|CONNECTING|HANDSHAKING|JOINING|CONNECTED|SUSPECT|CLOSED`, reason:string?；CONNECTED 指已加入房间 |
| GatewayError | code:string, message:string, recoverable:boolean, requestId:string?；本地错误 requestId=null |
| InputFrame | 完整 R3 字段见第 13.2 节；替换原基础版定义 |
| MatchInit | matchId:string, policePlayerId:string, thiefPlayerId:string；角色不同且非空。初始 pose 来自地图，tick=0 |
| StepInput | 完整 R3 字段见第 13.2 节；替换原基础版定义 |
| PlayerCommand | 完整 R3 字段见第 13.2 节；替换原基础版定义 |
| Departure | playerId:string, reason:`QUIT|BACKGROUND|DISCONNECT`；同一步相同玩家去重 |
| StepResult | 完整 R3 字段见第 13.2 节；替换原基础版定义 |

B 管理 250ms 输入租约：到期向本步引擎提交归零释放命令；该内部命令不消耗网络 inputSeq，PlayerCommand 此时沿用最后 inputSeq，A 的去重只过滤相同序号的离散 dropId，不能忽略租约释放。不得另行增加第二套 expiredPlayerIds 解释。本版固定采用归零命令，并在 B 入队前完成网络 inputSeq 去重。

A 的 step 结束后再次调用必须返回同一结果且不改状态；非法 tick 或未知 playerId 为编程错误，记录并让 B 终止该房间 SERVER_ABORTED，不崩溃整个服务端。viewFor 未知玩家抛受控参数错误；B 不得把该异常信息直接发给其他玩家。

abort也必须在该房间逻辑线程调用，A生成winner=null的SERVER_ABORTED结果；B不得另造与引擎不同的结果。若引擎自身损坏导致abort也无法安全完成，B关闭连接并显示SERVER_ERROR，不能发送未经确认的胜负。

单步判定顺序与 visibilityChanged 的 R3 扩展以第 13.8 节为准；结束后不得推进 tick 或再次产生动作/传送事件。

## 2.1 共享几何 API（contracts.geometry.WorldGeometry）

A 提供、B 审核、C 复用；全部是纯函数，不读时钟、不访问网络，服务端判定与客户端绘制必须使用同一套实现：

```java
boolean canStand(MapDefinition map, double x, double y, double r)
double  distance(double x1, double y1, double x2, double y2)
boolean segmentBlocked(MapDefinition map, double x1, double y1, double x2, double y2)
boolean inBeam(MapDefinition map, double px, double py, double headingRad,
               double tx, double ty, double range, double halfAngleRad)
boolean inViewRect(double px, double py, double tx, double ty,
                   double halfWidth, double halfHeight)
```

- 容差统一 1e-6；墙体为闭方块，擦墙角也阻挡视线（`segmentBlocked` 返回 true）。
- `inBeam` 同时检查距离、与朝向夹角、墙体遮挡；距离为 0 时只跳过夹角检查，仍做墙体遮挡检查。此纯几何函数不接收、不判断保护状态；A 在规则层结合 Protection 决定可见性和标记累计，C 不重复实现该权威判定。
- `inViewRect` 是小偷观察警察的矩形范围，包含边界，不受墙遮挡。
- `canStand` 同时要求不出地图边界、不与墙重叠；地图外不可走。

C 只能用这些方法绘制光束与对手可见范围，不能用本地几何覆盖服务端对 `opponent` 的决定（见第 7 节）。

## 3. WebSocket 通用包络

所有消息为一个完整 UTF-8 JSON 文本对象，不在一个 frame 内拼多条对象，不使用二进制。单消息最大 64KiB（UTF-8 字节）；超过限额拒绝并关闭。应用消息队列设上限，快照允许丢旧保新，控制/结果不得静默丢弃。

```json
{"v":2,"type":"INPUT","seq":12,"requestId":null,"matchId":"m-001","body":{"inputSeq":7,"moveX":1.0,"moveY":0.0,"aimRad":3.141592653589793,"interactHeld":false,"dropId":null}}
```

| 字段 | 类型 | 契约 |
|---|---|---|
| v | int | 必须 2；HELLO 也使用该包络，版本不兼容返回错误后关闭 |
| type | string | 下列目录中的精确类型 |
| seq | long | 每连接、每方向从 1 严格递增；每条新消息占一个序号；重复或倒退丢弃并报告一次 STALE_MESSAGE |
| requestId | string? | 控制请求及 USE_ITEM 必填，1–64 字符；响应关联同值；广播、连续输入和心跳为 null。USE_ITEM 的关联规则见 13.3 |
| matchId | string? | INPUT/USE_ITEM/动作结果/公开事件/结果确认/游戏视图/结果须为对应局 ID；房间控制为 null；ERROR 使用对应请求的 matchId |
| body | object | 必须符合消息类型模型，不含完整 MatchState |

服务器不接受客户端 body 中 playerId、胜方、位置或计数；会话绑定决定发送者。服务器出站 seq 每个连接单独增长，不用房间共享序号。HELLO 返回 sessionId 仅用于诊断，不作为可跨连接恢复的 token。

请求处理语义：可靠有序 WebSocket 上不做应用自动重发；UI 控制按钮等 onControl 的终态再解锁（B 内部关联 ACK/ERROR），2 秒未响应提示等待，5 秒无响应关闭连接。若重复 requestId 到达且请求类型/内容一致，返回缓存原 ACK/ERROR，不重复执行；内容不同返回 REQUEST_ID_REUSED。缓存当前连接最近 128 个控制结果；淘汰后的旧请求不得自动补发。输入按 inputSeq 去重，dropId 在本局内单调增长且仅消费一次。包络 seq 防过期消息，requestId 防控制重执行，inputSeq/dropId 防动作重复，职责不同。

## 4. 客户端 → 服务端消息全集

每一条均受包络约束；表中列出 body 的全部字段。

| type | body | requestId / matchId | 合法状态、处理与响应 |
|---|---|---|---|
| HELLO | clientBuild:string, mapHash:string, configHash:string | 必填 / null | 新连接第一条；验证版本与资源，响应 WELCOME；3秒内未收到关闭 |
| JOIN_ROOM | roomId:string | 必填 / null | WELCOME 后；创建或加入房间，ACK 后发送 ROOM_STATE；一个连接只加入一个房间 |
| SELECT_ROLE | role:Role | 必填 / null | LOBBY/COUNTDOWN；占位串行处理，变更取消倒计时并清双方准备；选原角色为无副作用成功 |
| SET_READY | ready:boolean | 必填 / null | LOBBY/COUNTDOWN；true 需要已有角色；false 取消倒计时并清双方准备；重复同值无副作用 |
| INPUT | 第 13.3 节完整 body（含 aimRad） | null / 当前局 | 仅 RUNNING；快照确认 inputSeq；警察可交互拾道具但不能 drop |
| USE_ITEM | actionId:long, slot:int, expectedItemId:string | a:动作ID / 当前局 | 见 13.3；返回 ACTION_RESULT，不走 ACK |
| HEARTBEAT | nonce:long | null / null | WELCOME 后任何阶段，每秒；PONG 原样回 nonce |
| LEAVE_ROOM | reason:`QUIT|BACKGROUND` | 必填 / null | 已入房间任意阶段；RUNNING 时转成 Departure；ACK 后解除成员关系并关闭该连接 |
| RETURN_LOBBY | resultId:string | 必填 / 当前局 | FINISHED；必须匹配结果；ACK 后 ROOM_STATE；重复请求幂等 |
| RESULT_ACK | resultId:string | null / 当前局 | FINISHED；停止本连接重复 GAME_OVER，不改准备或房间状态 |

INPUT 的 inputSeq 在每个 matchId 从 1 起递增。B 在发送 dropPressed 时分配 dropId 从 1 起递增；同一 drop 脉冲只发一次，后续 input 的 dropId=null。游戏输入在 RUNNING 前、结束后、旧 matchId、未知/越界数值一律拒绝。网络接受合法输入不等于玩法操作成功，是否可拾取由后续快照决定。

RUNNING时LEAVE_ROOM必须先排入本步Departure，保持会话到规则提交结果，再依次尽力发送GAME_OVER、ACK并解除房间/关闭连接；不能先删除成员导致引擎无法识别退出者。另一方正常收到结果。后台或网络已关闭的一方不保证收到结算；回到前台显示中断，不能猜测服务器最终结果。大厅和结算期离开直接ACK并清理，无需创建新结果。

已加入房间的连接再次JOIN_ROOM：同房间为无副作用成功并重发ROOM_STATE；其他房间返回INVALID_PHASE，必须先离开并重新连接。SELECT_ROLE/SET_READY等请求只能影响当前会话自己的角色和准备状态。

## 5. 服务端 → 客户端消息全集

| type | body | requestId / matchId | 处理 |
|---|---|---|---|
| WELCOME | sessionId:string, playerId:string, protocolVersion:int, mapHash:string, configHash:string, heartbeatMs:int, disconnectMs:int | HELLO 的值 / null | 启动心跳，自动 JOIN_ROOM；哈希必须与请求一致 |
| ACK | action:string | 请求值 / 请求值 | 仅表示控制动作已接受；客户端仍以 ROOM_STATE 为占位/准备依据 |
| ERROR | code:string, message:string, fatal:boolean | 请求值或 null / 对应值或 null | message 为显示文字，不含堆栈；fatal=true 后关闭 |
| ROOM_STATE | RoomState | null / null | 大厅、倒计时、运行、结算状态变更即广播；倒计时每100ms广播 |
| SNAPSHOT | PlayerView | null / 当前局 | 全量角色视图，替换旧视图；不做字段合并或保留消失敌人 |
| ACTION_RESULT | ActionResult（13.2） | USE_ITEM 的值 / 对应局 | 仅操作本人，见 13.3 |
| PUBLIC_EVENT | PublicEvent（13.7） | null / 对应局 | 双方传送提示，与活动快照共同去重 |
| GAME_OVER | MatchResult | null / 当前局 | 幂等展示结算、停止输入；B 自动 RESULT_ACK；接收后不再应用该局旧快照 |
| PONG | nonce:long, serverTimeMs:long | null / null | serverTimeMs 为进程单调时间毫秒，不是日期；用于 RTT/显示估计，不授予客户端判定权 |

ROOM_STATE 中 RUNNING 先于首个 SNAPSHOT 发送；首个 SNAPSHOT 含 tick=0 或服务器当前步，客户端收到两者后开始操作。GAME_OVER 前可发终局 SNAPSHOT，但客户端不能依赖它必须到达；GAME_OVER 自带完整结算字段。

## 6. RoomState 完整模型

```text
roomId:string
revision:long                 # 房间状态变化时递增，倒计时更新时间也递增
phase:RoomPhase
mapId:string
mapHash:string
configHash:string
matchId:string?               # RUNNING/FINISHED 非null；LOBBY/COUNTDOWN null
countdownRemainingMs:int      # COUNTDOWN 为0..3000，其他为0
players:[RoomPlayer]          # 长度0..2，按加入顺序
RoomPlayer = {playerId:string, role:Role?, ready:boolean,
              connection:"CONNECTED"|"SUSPECT", returned:boolean}
```

客户端自身 playerId 由 B 从 WELCOME 提取并通过 onSession(SessionInfo) 交付给 C，必须先于首次 onRoom，据此标记“我”；没有用户名或登录。returned 只在 FINISHED 有意义，其他阶段 false。对局中 connection 显示网络健康，不包含任何敌方坐标或保护状态。哈希不匹配不能开局。

## 7. PlayerView 完整模型与权限

R3 完整模型唯一维护于第 13.4 节。原基础字段保留，新增库存、效果、公开地面道具/卡、通道和传送；interaction 从 ThiefPrivate 移至 PlayerView 顶层。不要继续生成旧 ThiefPrivate.interaction。

权限沿用原规则：警察 thief=null，只得到公共物资起点状态与交付总数；看见小偷时 opponent 才含普通角色位置和 carrying 外观，隐藏时整体 null。小偷 groundMaterials 包含全部地面任务物资；警察角色可见范围仍为原矩形规则。公开地面道具/卡及传送光球是明确新增的信息权限，不使其他私有字段公开。

serverTimeMs 与 ackInputSeq 由 B 在 A 的语义视图副本中补齐（A 默认为 0）；其余字段由 A 生成。完整可解析角色样例见 [v2 fixtures](fixtures/v2/README.md)。示例坐标不是正式地图布局。

## 8. MatchResult 完整模型

```text
resultId:string                 # 一局唯一，建议 matchId + ":result"
matchId:string
winner:Role?                    # ABORTED 时null
reason:"TIMEOUT"|"CAPTURED"|"ESCAPED"|"QUIT"|"BACKGROUND"|
       "DISCONNECT"|"BOTH_LEFT"|"SERVER_ABORTED"
departedPlayerId:string?        # 单方异常时玩家ID，其他null
elapsedTicks:int                # 0..5400
marks:int
deliveredCount:int
finalTick:long
```

本人胜负由客户端以 winner 与自己 role 映射为 WIN/LOSE；winner=null 显示“对局中断，无有效胜负”，不是平局计分。相同 resultId 的重复结果只处理一次；内容不同为服务端缺陷，客户端保留首个并记录。结果不含敌人终点、交付地点或本局轨迹。elapsedTicks 为服务器行动开始后的实际模拟步数，3秒倒计时不包括在内。

同一步同时满足多个收尾条件时，按 V1 §8.2 的优先级：超时 > 第三次标记 > 撤离成功。本步的退出/后台/掉线事件只在没有正常收尾时生效，正常收尾优先；若双方同时失联且无法区分先后，结果 BOTH_LEFT、winner=null。已结算的结果不能被后续异常覆盖（决策 D08）。

## 9. 错误码与恢复

| code | fatal | 说明及客户端动作 |
|---|---|---|
| BAD_MESSAGE | false，连续3次后true | JSON/字段/类型/未知字段不合法；控制操作恢复可点击 |
| MESSAGE_TOO_LARGE | true | 超过64KiB，关闭 |
| VERSION_MISMATCH / MAP_MISMATCH / CONFIG_MISMATCH | true | 显示更新或资源不一致，返回连接页 |
| HANDSHAKE_REQUIRED / HANDSHAKE_TIMEOUT | true | 未完成握手或超时，重新连接 |
| INVALID_ROOM_ID / NOT_IN_ROOM | false | 更正房间或先加入 |
| ROOM_FULL / ROOM_BUSY | false | 已有两人返回 ROOM_FULL；有空位但处于 COUNTDOWN/RUNNING/FINISHED 返回 ROOM_BUSY，等待大厅后再加入，不踢已有玩家（沿用协作资料 R1 的错误码） |
| ROLE_TAKEN / ROLE_REQUIRED | false | 重新选择角色；不本地覆盖槽位 |
| INVALID_PHASE / STALE_MATCH | false | 不执行操作，等待当前房间/快照 |
| INVALID_INPUT / INVALID_ACTION | false | 越界非有限输入或角色无权动作；丢弃该命令，保留最近合法输入直到租约到期 |
| STALE_MESSAGE / STALE_INPUT | false | 旧序号丢弃，同类每秒最多反馈一次避免错误风暴 |
| REQUEST_ID_REUSED | false | 相同请求ID不同内容，拒绝 |
| RESULT_MISMATCH | false | 结果确认/返回请求与本局不符 |
| RATE_LIMITED | false，持续3秒后true | 输入超60/s或控制超10/s；拒绝超额并记诊断 |
| SERVER_BUSY | true | 建议首版最多8房间；达到上限拒绝新连接/建房 |
| SERVER_ERROR | true | 无法恢复的服务端会话错误，不能伪造胜负 |

本地 GatewayError 补充：INVALID_ADDRESS、CONNECT_TIMEOUT、CONNECTION_LOST、ALREADY_CONNECTED、NOT_CONNECTED；不发给服务器。结构合法但游戏条件不足（例如光照外、不可拾取）不反复 ERROR，按快照 candidate/blockedReason 表达。

## 10. 关键时序与背压

```text
C点击连接 → B建立WS → HELLO → WELCOME → JOIN_ROOM → ACK + ROOM_STATE
选择角色 → SELECT_ROLE → ACK + ROOM_STATE
双方准备 → SET_READY → ACK + ROOM_STATE(COUNTDOWN)
90步倒计时 → ROOM_STATE(RUNNING,new matchId) → SNAPSHOT
触摸 → INPUT → B入队 → A.step → A.viewFor(各玩家) → SNAPSHOT
规则结束 → GAME_OVER → RESULT_ACK → UI结算
各自返回 → RETURN_LOBBY → ACK + ROOM_STATE → 全员返回后LOBBY
```

网络回调给每房间入队；在固定步开始时原子取走当时所有待处理命令。迟到命令下步处理，不回滚历史。FIFO 处理控制与动作，连续移动可只保留最近值，但释放、按下、drop 脉冲必须按序保留。每连接输入队列建议128项，满时终止问题会话并走掉线流程，不能静默丢掉释放事件。

当前实现选择每连接最多 128 条尚未消费完的入站消息（包括文本、二进制和心跳），在进入逻辑执行器之前计数。超过上限立即终止该连接，并由原逻辑线程处理 DISCONNECT；该连接的待处理消息不再执行。未超额连接保持 FIFO，容量在消费完成后释放。超大文本在入队前识别，队列只保存拒绝动作，不保留超大载荷。`INBOUND_QUEUE_FULL` 是服务端诊断/传输关闭原因，不是新增应用 ERROR 消息码；强制断开不保证客户端收到该关闭原因。

出站每连接最多保留一个尚未发送的快照，新快照替换旧快照；控制/结果独立有界队列64项，满时关闭慢客户端。隐藏事件产生的最新快照覆盖旧可见快照，但不可让旧快照在新快照后发送。客户端只接受更高 tick（或第一次同tick终局更新），按同一连接 seq 处理。跨局先清空插值/按键缓存，再接新局快照。

Fugitive等外部项目参考或移植的实现必须适配本文接口，不将Godot节点、RPC对象或上游私有协议带入contracts。复用类型和来源按[开源方案](06_开源参考与复用方案.md)登记；发现必须调整接口时先更新契约、示例与三方实现。

服务端日志只记录 roomId、matchId、seq、错误码、状态跃迁和受控诊断；客户端正常日志不输出对手隐藏位置。调试全状态只可在服务端受控测试中使用，不加入发布消息或 UI 开关。


## 12. R2 协作补全（规范性要求）

本节将前述接口细化为唯一实现方式；不是可选方案。本节保留基础房间控制、输入归并和严格校验要求；R3 已升级目标协议为 v2。类型、可空字段和新增动作以第 13 节替换定义为准。

### 12.1 身份与控制操作回调

SessionInfo = {sessionId:string, playerId:string}。仅进程内回调，不是新网络消息。WELCOME 校验成功后先 onSession，再发送 JOIN_ROOM；首次 onRoom 前身份必须可用。开始新连接及连接关闭时 onSession(null)，C 同时清除身份、旧房间及旧对局缓存，不能按房间列表顺序猜自己。

WELCOME 必须关联当前连接中尚未完成、未超过 5 秒控制期限的 HELLO requestId；错误关联、重复或晚到的 WELCOME 不得发布身份或触发 JOIN_ROOM。服务端方向首条包络 seq 必须为 1，后续严格递增即可，不要求连续无间隔；新连接重新从 1 校验。

ControlStatus = {requestId:string, action:string, state:State, errorCode:string?}。State 为 PENDING、WAITING、SUCCEEDED、FAILED、TIMED_OUT、CANCELLED。requestId 由 B 生成，C 只关联回调，不创建网络序号。

- 每次控制请求先产生 PENDING；从该请求开始计时，2 秒没有响应只产生一次 WAITING，5 秒产生 TIMED_OUT 并关闭连接。心跳或其他请求成功不能延长本请求期限。
- 每个 requestId 恰有一个终态。ACK 的 action 必须匹配原请求；ERROR 对应 FAILED；断开导致尚未完成的请求 CANCELLED。重复/晚到 ACK 不再产生终态。请求关闭后不自动重发。
- HELLO 由 WELCOME 完成，其他控制请求由 ACK/ERROR 完成。自动 HELLO/JOIN_ROOM 也走回调，C 可将它们归入连接状态展示。
- PENDING/WAITING 时 C 禁用对应操作；终态解除等待。客户端方法仍返回 void，回调可能在方法返回前触发，因此 C 不得依赖返回后才建立请求跟踪。
- SUCCEEDED 仅表示请求被接受。角色、ready、returned 等权威状态仍从 ROOM_STATE 获取，不能用成功回调自行改角色槽。
- 本地未连接等失败也应给出 PENDING→FAILED，错误码 NOT_CONNECTED。尚未调用 connect、没有 listener 时不接收用户控制操作，C 禁用控件。
- errorCode 在 PENDING/WAITING/SUCCEEDED 时为 null；FAILED 为业务错误码，TIMED_OUT 为 CONTROL_TIMEOUT，CANCELLED 为 CONNECTION_CLOSED。onError 仍用于统一错误显示，不能再次结束同一请求。
- background 尽力发 LEAVE_ROOM 后立即关闭，不保证 ACK；对应请求可终止为 CANCELLED。这不表示服务器已经完成判负。

### 12.2 A/B 单步输入解释

B 在步边界一次性交付 FIFO commands；A 不以消息数推进时间。每名玩家的连续输入跨步保留，初始零输入。输入租约到期由 B 插入零输入/释放命令，沿用最后 inputSeq，dropId=null，不能被 A 的序号去重误删。

每步按以下规则归并，不允许 A/B 各选实现：

1. 按该玩家命令顺序扫描全部边沿，释放立即取消已有交互、清除 requiresRelease；按下仅记录本步最终仍按住的一次启动意图，不增加进度。若出现释放再按下，旧进度清零。
2. 移动方向采用本步最后一条命令；无命令沿用上步。整步只移动一次（1/30 秒），不能每条命令移动一次。只要本步任一有效命令包含非零移动，或最终沿用非零移动，本步视为有移动尝试：取消交互、要求释放，本步不启动交互，即使最终停止或撞墙。
3. 对每个新 dropId 按序去重并消费；本步存在有效丢弃脉冲就取消交互，本步不启动/累计交互。丢弃位置取本步移动后的脚下位置；同一步多个脉冲至多丢出原来携带的一个物资。
4. 无移动/标记/丢弃等取消条件时，最终仍按住且有合法新按下才选择本步移动后位置的目标。保持按住仅继续原锁定目标，不能重新选目标。累计最多一次；新开始的合法按住计第 1 步。
5. 取消发生在本步后续规则阶段时，本步较早收到的释放不能预先解除该取消锁。若最终 held=false，则视为已经释放，下一步的新按下可启动；若最终 held=true，则必须在之后收到释放。
6. 同步异常与正常结局优先级不变。多条命令只影响该步输入，不增加照射/交互/对局计时步数。ackInputSeq 是已消费的最高合法网络 inputSeq，内部租约命令不增加它。

| 起始状态 | 同一步命令（按收到顺序） | 本步预期 |
|---|---|---|
| 静止、无交互 | 按下→释放 | 不启动、不累计 |
| 已累计 12 步 | 释放→按下，静止合法目标 | 旧进度清零，新的交互为 1 步 |
| 已累计 12 步 | 移动→停止，始终按住 | 最终方向为零、不位移；取消进度，须之后释放 |
| 携带物资、按住 | 丢弃→释放→按下 | 本步丢弃，无交互，最终按住则须之后释放 |
| 任意 | N 条纯移动输入 | 按最终方向只移动一次，计时只走 1 步 |
| 按住交互 | 无新网络输入且租约到期 | B 归零释放，交互取消，不能无限累计 |

以上是完整引擎的验收表；S0 移动原型尚不支持完整交互，不能把该表标记为已经通过玩法测试。

### 12.3 消息校验与共享样例

B 在反序列化前验证结构：字段集合精确匹配；必填字段缺失必须拒绝（包括允许 null 的字段）；字符串/布尔/数值不得隐式互转；枚举值精确匹配；递归检查数组元素和嵌套对象；拒绝非有限数值。long 限 0..2^53−1，int 限 32 位整数。允许 null 的字段逐项列白名单，禁止全局放宽。

基础版可空白名单共 9 项（R3 删除/增加路径见 13.4），新增可空字段必须同时改本表、DTO 文档和 `BodyValidator`，缺一即视为契约变更：`RoomState.matchId`、`RoomPlayer.role`、`PlayerView.opponent`、`PlayerView.thief`、`ThiefPrivate.carriedMaterialId`、`InteractionView.candidate`、`InteractionView.active`、`MatchResult.winner`、`MatchResult.departedPlayerId`。`PlayerView` 另有一条强制约束：POLICE 时 `thief` 必须显式 null，THIEF 时必须为对象。

结构校验之后由接收状态机校验业务约束：ID 关联、matchId 一致、阶段、权限、范围、成员唯一性、单调 tick/revision、角色私有字段。结构通过不表示业务合法。警察 thief 必须显式 null，小偷必须为对象。

共享样例在 docs/development/fixtures/。room-lobby.json 是 RoomState body（不是完整包络），其中哈希为测试占位，不能直接用于真实握手。BodyValidatorTest 直接读取此文件，并生成缺字段、非法枚举、错误 null、类型混淆及嵌套未知字段反例。新增消息样例沿用此目录；B 维护，A/C 审阅。

本轮已实现 DTO 递归结构校验及已有大厅控制 body 检查；这些是基础版历史实现记录；R3 完整消息和业务语义验证仍是 B 迁移时的必做项，不能声称协议全量验收完成。

## 13. R3 新功能完整契约（目标 v2，待代码实现）

### 13.1 版本、单位与字段规则

- R3 升级包络 v、WELCOME.protocolVersion 和编译期 Protocol.VERSION 为 2；v1 客户端拒绝入局，返回 VERSION_MISMATCH 后关闭。不同时支持两套玩法协议。
- 世界坐标沿用左下原点，x 向右、y 向上；距离单位为地图格。角度为弧度，0 向右、逆时针增加，输入/输出均在 [0,2π)。所有 double 必须有限。
- 逻辑 tick 为 30Hz；所有 untilTick/endTick 都是**不包含该截止步**的绝对截止。开始于 k、持续 d 步的效果在 k..k+d−1 有效，k+d 先到期再处理该步动作。数值限制沿用第 1 节。
- 本节代码块中的字段集合是完整定义。`T?` 为必填可空字段，数组不得 null；禁止出现未列出的字段。新 ID 为非空字符串、至多 64 字符、大小写敏感；地图定义 ID 全局唯一，运行实例 ID 在本局唯一。
- ItemType=`SPEED_BOOST|LIGHT_BOOST|SHIELD`；EffectType 同 ItemType。加速共用一种类型，地图 ownerRole 区分归属。LIGHT_BOOST 只允许 POLICE，SHIELD 只允许 THIEF。
- InteractionType=`PICKUP|DELIVER|ESCAPE|PICKUP_ITEM|PICKUP_CARD|UNLOCK_PORTAL|ENTER_PORTAL`。前三项仍为原任务物资流程。

### 13.2 C → B 输入接口与 B → A 命令

下面替换第 2 节对应类型，其余已有方法保留。R3 类型统一位于 com.lightchase.contracts.v2，无 Android/libGDX/socket 依赖；未变化基础类型仍复用原 contracts 包。DTO 使用不可变 record，Java 调用使用 accessor，JSON 字段名保持本文定义。

```java
// ClientGateway 新增：B 生成 actionId，C 只传槽位和当前看到的实例 ID。
void useItem(int slot, String expectedItemId);
// GatewayListener 新增：串行回调，C 入渲染队列。
void onAction(ActionStatus status);
```

```text
InputFrame = {moveX:double,moveY:double,aimRad:double?,
              interactHeld:boolean,dropPressed:boolean}
PlayerCommand = {playerId:string,inputSeq:long,moveX:double,moveY:double,
                 aimRad:double?,interactHeld:boolean,dropId:long?}
PlayerAction = {playerId:string,actionId:long,slot:int,expectedItemId:string}
StepInput = {tick:long,commands:[PlayerCommand],actions:[PlayerAction],
             departures:[Departure]}
ActionResult = {matchId:string,actionId:long,slot:int,expectedItemId:string,
                success:boolean,code:string,appliedTick:long}
PlayerActionResult = {playerId:string,result:ActionResult}
StepResult = {tick:long,visibilityChanged:boolean,ended:boolean,
              result:MatchResult?,actionResults:[PlayerActionResult],
              events:[PublicEvent]}
ActionStatus = {matchId:string,actionId:long,slot:int,expectedItemId:string,
                state:PENDING|SUCCEEDED|FAILED|TIMED_OUT|CANCELLED,
                code:string?,appliedTick:long?}
```

- moveX/Y 各在 [-1,1]，对角线归一化沿用原移动规则。aimRad=null 表示不更新手电朝向；警察首次方向取出生朝向，之后保持最后有效瞄准。小偷必须发送 null。移动不改变警察手电方向。
- C 每帧提交 InputFrame；B 仍以 20Hz 和边沿即时发送。租约到期归零移动、释放交互、dropId=null、aimRad=null；保留合法手电方向。连续瞄准无一次性动作含义。
- 警察现在允许 interactHeld 拾取本角色道具；警察 dropPressed=true 仍拒绝。两种角色均不能丢弃道具或门禁卡。
- useItem 只在 RUNNING、已连接且非 SUSPECT 时接受。slot 只能 0/1，expectedItemId 非空。C 在该槽有 PENDING 时禁用该槽再次点击；可操作另一槽。库存仅随 SNAPSHOT 更新，回执不直接删槽。
- B 按每局从 1 递增分配 actionId，先回调 PENDING，再发送 USE_ITEM。5 秒未收到结果则 TIMED_OUT/ACTION_TIMEOUT 并关闭连接；断开/新局终止未完成操作为 CANCELLED/CONNECTION_CLOSED，不自动重发。无有效局/连接等本地失败给 onError，不发送也不分配 actionId。
- ActionStatus 在 PENDING 时 code/appliedTick=null；成功为 SUCCEEDED/OK/实际 appliedTick；业务失败为 FAILED/错误码/判定 tick；本地超时/取消 appliedTick=null。每个 actionId 恰有一个终态，晚到或重复结果不再次回调。
- A 收到 commands/actions 时身份已由 B 绑定，不能接受客户端 playerId。动作结果含 playerId 只用于服务端路由，线上 ACTION_RESULT 不含该字段。
- B 保留每个玩家的动作接收顺序，A 对 actionId 去重并验证期望实例。连续输入与离散道具操作分别交付；本步输入先归并，动作在第 13.8 节指定阶段执行。

### 13.3 新增/替换线上消息

| 方向/type | body 的全部字段 | requestId / matchId | 语义 |
|---|---|---|---|
| C→S INPUT | inputSeq:long, moveX:double, moveY:double, aimRad:double?, interactHeld:boolean, dropId:long? | null / 当前局 | 替换原 INPUT；SNAPSHOT.ackInputSeq 只确认连续输入 |
| C→S USE_ITEM | actionId:long, slot:int, expectedItemId:string | a:动作ID / 当前局 | 一次性使用；仅 RUNNING；不走控制 ACK |
| S→C ACTION_RESULT | ActionResult | USE_ITEM 的值 / 对应局 | 只发给操作玩家；成功/业务拒绝均一条结果 |
| S→C PUBLIC_EVENT | PublicEvent | null / 对应局 | 成功传送时给双方各发一次，供提示/音效；不放隐藏角色位置 |

USE_ITEM.requestId 固定为字符串 `a:<actionId十进制>`，ACTION_RESULT 和相关 ERROR 回传同值及原 matchId，以便 B 精确结束对应 PENDING。该前缀专供道具动作，普通控制请求不得使用；这些消息不触发 onControl、不走控制 ACK 或控制请求缓存，动作缓存以 matchId+playerId+actionId 为键。

USE_ITEM 的 actionId 为正整数，每局每玩家严格增加，允许不连续。B 对重复且内容相同的 ID 返回最近 128 条缓存的原 ACTION_RESULT；内容不同返回 ERROR/ACTION_ID_REUSED；低于最高已见 ID 且缓存已淘汰的动作返回 ERROR/STALE_ACTION，绝不再次执行。尚在处理的相同动作合并，待结果后回复，不能入队两次。A 同样用最高已处理 ID 和有限缓存防御重复，缓存淘汰后拒绝旧 ID。

结构/数值/未知字段错误走 ERROR/BAD_MESSAGE 或 INVALID_INPUT；不分配玩法结果。结构合法的使用请求进入 A，由 ACTION_RESULT 表示业务成功/失败。旧局请求走 ERROR/STALE_MATCH，非运行期走 ERROR/INVALID_PHASE；B 终止匹配的 PENDING 为 FAILED，不改变已锁定结算。ERROR/ACTION_ID_REUSED、STALE_ACTION 同理。非致命错误不会让另一个动作失败。

成功 success=true、code=OK；失败 success=false、不消耗道具。code 使用以下精确值：

| code | 条件 |
|---|---|
| EMPTY_SLOT | 槽为空 |
| ITEM_INSTANCE_MISMATCH | 槽有物品但与 expectedItemId 不同 |
| ROLE_FORBIDDEN | 道具不属于本人角色 |
| EFFECT_ACTIVE | 加速或光照同类效果尚未结束 |
| IN_TRANSIT | 正在传送中 |
| MATCH_ENDED | 动作已入队，但处理时对局已结束 |
| STALE_ACTION | A 检测到无法安全重放的旧动作 |

失败检查顺序：对局已结束 → 去重/期望 ID 检查（空槽优先）→ 角色 → 传送 → 同类效果。只有成功后在同一步原子清空指定槽并应用效果。重复成功返回原结果而非重新校验已空槽；不触发第二次效果。新局清缓存、计数及待发送动作，旧包不能映射到新局。

### 13.5 拾取、解锁和交互锁定

- 两角色均有独立 InteractionView。小偷在真隐身时禁止全部交互：任务拾取/交付/撤离、道具/卡拾取、解锁、进入传送。IMMUNE 可正常交互。传送中双方操作限制按 13.7。
- 候选先过滤角色、状态、容量、对应卡、任务条件、距离和可达交互条件，再按脚下到目标的欧氏距离升序；同距离（容差 1e−6 内）按 targetId 的 Unicode 字典序排序。距离不大于 interactRange，且到目标中心 segmentBlocked=false；开始后锁定 type/targetId，不因新近目标出现改选。
- 任务物资类型沿用原条件；PICKUP_ITEM 指向 itemId，PICKUP_CARD 指向 cardId；UNLOCK_PORTAL、ENTER_PORTAL 指向 portalId，仅在该通道**入口**交互，出口无候选。卡片和入口的对应关系由 portalId 判断。
- InteractionTarget.expectedCardId 仅在 UNLOCK_PORTAL 时为当前匹配卡实例 ID，其他类型必须 null。开始时锁定它，完成时再次验证，避免旧交互扣后来拾到的新卡。客户端不能直接指定 unlocked 或卡槽结果。
- 进入新交互必须收到新的按下边沿、保持静止；开始步计 1，达到该类型 requiredTicks 才完成。完成后 requiresRelease=true，按住不连锁拾取/传送。解锁成功仅开门扣卡，必须松开再按才能 ENTER_PORTAL。
- 移动尝试（包括撞墙）、松开、目标消失/不再合法、被标记、有效护盾、丢弃任务物资会取消进度；除松开外最终仍 held=true 时设置 requiresRelease。加速/光照使用不主动取消交互，实际移动仍取消。
- 既有同 tick 按下/释放归并沿用 12.2，但现在对两角色运行，并加入护盾/传送中断。一次持续按住不生成独立解锁网络请求，不能由 B 重放成第二次交互。
- 拾道具放入最低索引空槽，地面 itemId 原样进入库存；成功后地图实例移除。满槽拒绝、无自动替换、无补货。卡独立保存至 thief.card，已有卡拒绝，无丢卡/换卡动作。
- 正确解锁在同一步原子设 unlocked=true、revision+1、销毁对应卡、card=null；失败不改任何一项。重复/迟到交互不能再次扣卡；已解锁不再提供 UNLOCK_PORTAL 候选。

InteractionBlock=`NONE|INVISIBLE|MOVING|NO_TARGET|RELEASE_REQUIRED|IN_TRANSIT|INVENTORY_FULL|CARD_SLOT_FULL|CARD_REQUIRED|WRONG_CARD|ROLE_FORBIDDEN|TARGET_GONE`。

有效 candidate/active 时 blockedReason=NONE，requiredTicks 为该类型配置时长，未活动时 progressTicks=0。无目标时 requiredTicks=0。优先理由为 IN_TRANSIT → INVISIBLE → MOVING → RELEASE_REQUIRED；若没有合法候选，再取最近范围内相关不可执行目标的拒绝理由；没有任何相关目标为 NO_TARGET。错误通道为 WRONG_CARD，无卡为 CARD_REQUIRED。被别人拾走或条件变化导致正在锁定目标失效，取消当步为 TARGET_GONE，随后重新计算候选。按钮的失败理由仅给本人，不广播其隐藏交互位置。

### 13.6 道具效果与保护截止

- SPEED_BOOST：effectiveSpeed=基础 speed×speedBoostMultiplier；LIGHT_BOOST：effectiveRange=基础 beamRange×lightBoostMultiplier，halfAngleRad 不变。两者可同时生效，同类型尚有效时拒绝使用且不扣槽；效果截止后可立即再次用。使用不要求静止。
- SHIELD：清 beamProgress，不改 marks，不走成功标记路径；取消正在交互。NORMAL/INVISIBLE/IMMUNE 均可使用。令 k=当前 tick、d=shieldTicks：invisibleUntilTick=max(k+d,旧 invisibleUntilTick)。两件分别消耗，不叠加时长、不缩短已有真隐身。
- markImmuneUntilTick 仅由成功标记设置，不因护盾改变或延长。保护状态计算**先检查真隐身**：若 k<invisibleUntilTick 则 INVISIBLE；否则若 k<markImmuneUntilTick 则 IMMUNE；否则 NORMAL。不能沿用旧实现“先判断免疫是否到期就清空全部保护”，否则护盾比免疫长时会被截断。
- 成功标记仍设置 invisibleUntilTick=k+invisibleTicks、markImmuneUntilTick=k+invisibleTicks+immuneTicks；第三次标记直接结算。护盾不创造免疫尾段；保护期间不产生新标记，历史标记保持。
- 示例：原免疫截止 tick=120，在 tick=0 用 90-tick 护盾；0..89 真隐身，90..119 免疫，120 正常。若护盾持续到 150，则 120..149 仍真隐身、150 直接正常。数值仅解释时序，不是游戏平衡参数。

### 13.7 通道、传送事件与客户端表现

- 地图恰好两条有向通道、四个不同端点；开局均锁定，各有一张对应卡；解锁本局永久有效，新局恢复。仅小偷能解锁/进入；可携任务物资穿越；无额外冷却。
- ENTER_PORTAL 完成时创建唯一 transitId，startTick=当前 tick、endTick=startTick+transitTicks。起步普通角色隐藏，不再以地表角色绘制；在当步照射/标记之后才启动，不能躲掉该步已经完成的标记。
- startTick..endTick−1 禁止移动、交互、用道具和再次传送，不参与地表照射；原有效果和时间继续走。输入可更新/释放缓存，但不产生移动或交互进度；到达步清空旧移动/按住（含本步归并的旧输入），本步不移动或启动新交互；设 requiresRelease，收到到达后的释放才能接受新按下。C 在到达时释放虚拟控件，仍按着的手指须先抬起，禁止把入洞前长按带到出口。新鲜移动输入从下一步恢复。

### 13.8 权威单步顺序与新局清理

以下替换旧开发设计的单步顺序：

1. 若已结束，返回固定结果且不推进；拒绝新动作。验证步号/身份、归并连续输入及释放边沿。
2. tick 前进；过期加速/光照/保护刷新；活动传送到 endTick 则落地并清旧输入。
3. 按每玩家动作顺序处理本步 USE_ITEM，生成结果，先应用有效效果。已经传送中的使用拒绝。护盾造成的交互取消不能被该步更早的释放预先解除。
4. 地表玩家只移动一次，使用本步有效速度；更新独立 aimRad，计算有效光照。
5. 地表照射/标记，保护状态参与判定；发生标记取消交互；第三次标记锁定抓捕。
6. 处理任务物资丢弃；然后两角色交互各累计至多一次；小偷被标记/抓捕当步不完成交互。先完成拾取或解锁，传送启动发生在本阶段。
7. 正常结局按超时 > 抓捕 > 撤离；之后异常离开/后台/掉线；结果一经确定不可改。
8. 投影两份安全视图、动作结果及本步公开事件。若本步已结束，丢弃待发布传送开始事件、清除活动光球，避免结算后播放传送。visibilityChanged 还应在光照强化、拾取、解锁、保护变化、传送开始/结束及道具成功时置 true，B 立即发送新快照。

结束后重复 step 返回相同结果，actionResults/events 为空，避免重发业务；GAME_OVER 重投由 B 处理。终局同一步较早已成功的道具结果可先于 GAME_OVER 发出；不会撤销胜负，也不允许结束后的道具“复活”。尚未消费的队列动作以 MATCH_ENDED 结束，不再推进引擎。

新局清空库存、效果、卡槽、交互锁、解锁状态/revision、光球/事件、动作 ID/去重、旧输入和插值；重新生成固定地面道具/卡。C 清本地提示集合并重新建立姿态基准。回大厅、后台、断开与销毁均停止传感器采样；设备不支持时在游戏外回退触控。校准不暂停对局。
