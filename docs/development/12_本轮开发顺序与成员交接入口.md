# 本轮开发顺序与成员交接入口

日期：2026-11-16。面向 A（游戏规则）、B（网络）、C（Android/UI）。本文件是本轮交接的统一入口；详细任务沿用 [11 分工与联调](11_功能拓展分工与联调.md)，不另建一套任务编号。

**当前状态：用户已确认 E01–E12，正式接口文档已更新为 R3/v2。共享 v2 类型、严格 Codec 与固定配置已落地并验证，见 [13 接入说明](13_R3共享代码基线与接入说明.md)；引擎、网关、UI 与替身仍待接入，尚未发布完整 J0 代码包。**

## 1. 本轮最终要做什么

以[组员版功能说明](../requirements/2026-11-16_组员版功能拓展说明.md)和[实现基线](../requirements/2026-11-16_功能扩展实现基线.md)为准：

| 功能 | 必须保留的规则 |
|---|---|
| 双槽道具 | 每人两件独立实例；同类可占两槽；满槽拒绝且地面道具保留；与任务物资独立 |
| 四类角色道具 | 警察光照强化、加速；小偷加速、护盾。先固定生成，倍率、时间和点位配置化 |
| 护盾 | 清照射累计，不清历史标记；保护中也可消耗，新剩余真隐身取 max（配置时长、当前剩余真隐身）；不自动赠送免疫尾段 |
| 门禁卡 | 小偷独立单张卡槽；持卡拒绝拾其他卡；一卡对应一通道；正确解锁成功才销毁，失败不消耗 |
| 单向传送 | 仅小偷，从入口到出口，无额外冷却；传送中不重复启动；每次启动通知警察 |
| 公开光球 | 人物传送中变为直线飞行光球，双方可见；落地后恢复普通可见性，不继续公开隐藏坐标 |
| 小地图 | 复用现有 Minimap，移至右上角；自己是红点，通道锁定灰色、解锁换色；动态对象遵守角色权限 |
| 独立瞄准及陀螺仪 | 左移动；游戏外关陀螺仪时右瞄准摇杆，开启时右校准按钮；两种右侧控件互斥 |

先实现功能，之后再调平衡、正式地图与随机生成。早期双向暗道、传送冷却、静默装置和单道具槽建议已被后续决定替换。扫描建筑、真人 CS 等讨论不属于本轮任务。

## 2. 我们现在先做什么

按「核对工程基线 → 收敛规则 → 完成契约包 → 三人独立开发 → 逐功能联调 → 完整回归」推进。准备工作由 A 牵头，B 维护共享协议，C 审查输入和展示需求；不需要等 A 写完全部业务代码再让 B/C 开始。

### 第一步：确定大家拿到的是同一个项目

- 使用自己的 Light-Chase 仓库作为开发源；当前课业目录中的 docs 和旧 handoff ZIP 是快照。教师仓库用于课程交付。
- 发给成员可拉取的分支与完整提交 SHA，记录协议、地图、规则配置版本及 hash；本地未提交文件不算已交付。
- 阅读历史运行说明时核对当前代码及最新验证记录；旧记录中“尚未实现”的描述不能直接当作今天的工程结论。
- 记录基线构建结果和已有问题，后续区分新增回归与原有问题。

### 第二步：规则已由用户确认

已完成：用户在本次交流中采纳全部十一项规则及独立瞄准/校准约定，记录于 [04 决策表第 6 节](04_决策与待确认事项.md) E01–E12。无需等待三位成员另开会议确认玩法。完整规则见组员版功能说明第五节，精确字段、消息及状态时序已写入 [02 接口契约第 13 节](02_接口契约.md)。

最终平衡数值、精美地图和 C 的配色方案后置；这不阻塞当前协议实现。

### 第三步：把契约从说明清单变成可使用的交接包

正式契约 R3/v2 与可解析 JSON 样例现已具备；共享 v2 类型、Codec、配置已落地并验证；原运行端仍使用基础版，需要各成员按 R3 接入。消息样例已通过 V2WireCodec 测试，不适用于旧 Codec。

准备完成以下产物后再宣布本轮共享基线可用：

| 产物 | 谁维护/审核 | 必须达到什么程度 |
|---|---|---|
| 正式接口契约 | B 维护，A 审规则，C 审可用性 | 02 写明精确签名、字段、枚举、空值、单位、角度、tick、权限、错误与版本兼容策略 |
| 公共类型与编解码 | B 维护 | contracts 中可编译类型；输入到引擎、视图到快照的映射与严格校验同步；实现和文档一致 |
| 规则和测试地图配置 | A 维护 | 固定卡/道具点、通道 ID/端点、效果时长；合法落点；三方使用相同字节及 hash |
| 共享请求/快照样例 | B 存档，A 给预期结果，C 验证可展示 | 两角色各自视图，含成功与失败；能被正式 Codec 读取，不能只放伪 JSON |
| 替身入口 | A/B/C 分别维护 | A 的脚本能推进规则；B 的假引擎能产出合法视图；C 的脚本化假网关能切换共享场景 |
| 本轮任务及完成标准 | 沿用 11，A 统筹 | 每人第一项任务、允许修改目录、输入依赖、交付物、运行方式及验收条件明确 |

契约至少覆盖：独立瞄准、指定槽道具使用、卡与通道交互、库存/卡槽/通道/效果/光球状态、成功及失败回执。一次性操作关联 matchId、唯一操作标识和期望实例，明确重复/过期处理；原始陀螺仪数据留在 C 本地，只上传统一瞄准意图。

共享场景至少有：移动与瞄准不同向、两件同类道具、满槽拾取失败但能拾卡、持卡拒绝第二张、错卡失败、匹配解锁并消耗、护盾在正常/真隐身/免疫期间使用、通道锁定/解锁、传送中/落地、对手可见/隐藏、新局清理。样例应给初始状态、动作和预期结果，避免只有静态截图。

**共享基线放行条件：**三方拉取同一提交可编译；正式 Codec 能读取共享样例；A/B/C 均能通过已有接口接入自己的替身；尚未实现的业务列明。放行表示接口可以依赖，功能通过要等后续验收。

## 3. 给成员发什么，他们怎样开始

发「同一仓库/提交 + 本文件链接 + 自己在 11 中的任务段」。成员打开这一份入口即可找到相关资料；接口细节由 02 唯一维护，避免在三份任务书里复制后逐渐不一致。

| 成员 | 从哪里开始 | 独立开发方式 | 负责交付 |
|---|---|---|---|
| A：你 | 11 第三节；game-core、game-data | 固定 tick 和脚本动作，不等手机与网络 | 独立瞄准 → 双槽与效果/护盾 → 卡与解锁 → 单向传送/安全角色视图；规则结果与测试配置 |
| B | 11 第四节；contracts、server、client-network | 假引擎与两个 JVM 客户端，不等新规则完成 | 共享契约 → 操作传递/去重 → 完整快照与公开事件 → 可运行网关/服务器及联机记录 |
| C | 11 第五节；app、client-core、资源 | 脚本化假网关与共享快照，不等服务器 | 布局草图 → 双摇杆 → 双槽/卡槽/小地图 → 光球与反馈 → 陀螺仪/校准 → 真实网关注入 |

以上按本轮任务的依赖顺序执行，编号仍引用 11 的 A1–A9、B1–B7、C1–C9。旧 05 中“不添加钥匙/传感器”是基础版历史限制，本轮按上述已确认范围执行。

独立开发的边界：A 决定规则和可见性；B 搬运权威结果并校验协议；C 提交意图、展示结果。B 不重新计算护盾，C 不自行宣告拾卡成功，A 不调用 socket。C 的脚本化 UI 替身与复用 A 引擎的离线游戏模式要区分，前者用于稳定复现场景。

每位成员可复制给自己 AI 的启动说明：

> 我负责 Light Chase 的【A/B/C】部分，本次任务是 11 中的【编号和具体目标】。先读 12 交接入口、组员版功能说明、02 正式接口契约以及 11 对应角色任务，核对收到的共同提交和代码现状。只修改本角色负责模块；共享接口不足时提交具体契约差异，不私建 DTO。先用替身独立验证，再接真实模块。交付修改说明、实际运行命令及结果、样例和未完成项；不得以离线画面证明联机功能完成。

## 4. 开发与联调的工作顺序

共享契约稳定后，三人可以同时做各自模块；集成按下面的功能顺序推进，每次接通一小条完整链路：

1. **J0 共同基线：**版本、配置、样例和编译一致。
2. **J1 独立瞄准：**先用触控贯通 C 输入 → B 传输 → A 照射 → B 视图 → C 绘制；能后退并向前照射。
3. **J2/J3 道具与护盾：**固定生成、独立两槽、真实加速/光照、护盾清累计与 max 刷新。
4. **J4a 卡和解锁：**拾卡、满卡槽拒绝、错卡失败、成功原子消耗、两端通道换色。
5. **J4b/J4c 传送与小地图：**单向、无额外冷却、双方光球与提示、落地权限恢复；右上角红点与可见对象正确。
6. **J5 陀螺仪真机：**把传感器接入已经验证的瞄准入口，测试开关、校准、无传感器回退和前后台。
7. **J6 整局回归：**保留原任务、标记、撤离、超时、结算和重开；新局清除库存、卡、效果、光球、解锁和旧输入。

C 可以较早做传感器小原型；正式联机验收安排在统一瞄准链路之后。正式地图和平衡、随机生成放到本轮功能闭环后。详细通过条件使用 11 的 J0–J6 表，不另改标准。

## 5. 怎样保证独立开发不会越做越不兼容

- 各自在功能分支工作，共用可拉取的契约提交；不把整个项目复制成三个新工程。
- contracts、协议编解码、顶层构建由 B 协调；规则与地图由 A 维护；输入布局、美术和卡/通道视觉标记由 C 维护。
- 发现接口缺口时，提出「场景、现接口缺什么、拟改字段/语义、对另外两人的影响」。A/B/C 审完后由 B 同步 02、DTO、Codec、样例与验证，发出新提交和迁移说明。
- 功能状态分别记录为待开发、模块验证通过、联调通过、设备验证通过；旧测试数量与历史截图不能充当本轮证据。
- B 汇总联调问题，A 负责规则判定，C 负责显示与设备问题；每项明确负责人、复现方式和关闭条件。

每次交付附下面的短表即可：

```text
任务：11 中的编号 + 功能
共同基线/本次提交：
修改模块：
依赖的契约/配置版本：
运行与验证命令、实际结果：
交给其他人的入口/样例：
仍未完成或未验证的内容：
```

JVM 模块可用仓库现有 `./gradlew.bat checkJvm` 做回归；Android 构建为 `./gradlew.bat :app:assembleDebug`，服务端分发为 `./gradlew.bat :server:installDist`。成员还需附本任务的针对性验证与必要设备记录。本轮整理仅检查文档与链接，没有执行上述构建或功能验收。
