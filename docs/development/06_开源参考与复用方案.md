# Light Chase 开源参考与复用方案

日期：2026-10-23；R1。当前为选型与初步核查，尚未导入、移植或运行 Fugitive 源码。

## 1. 为什么现在记录

开源来源、预期复用范围、技术适配和团队新增贡献，应在开发设计阶段明确；具体函数、文件和修改量在源码阅读及实现阶段补齐。不能等完成后再寻找一个项目来补“参考来源”，也不能将仅仅相似的玩法写成已经复用代码。

项目现有课程材料的原文提取记录中，Outline指南要求指出可复用的开源代码，并鼓励利用开源项目；项目总指南强调许可允许的复用和明确标示他人代码来源。依据为仓库内 `guidlines/_tr/src/02 Guidelines for completing and submitting Android Project outlines.json` 与 `guidlines/_tr/src/00 App Project guidelines  Recommendations Updated 2026.json`。这些内容支持现在加入复用计划；尚不能据此推导出“必须fork一款完整游戏”或“只有直接复制代码才算合格”。如教师另有具体要求，按该要求调整。

## 2. Fugitive候选项目身份与证据

本轮按用户提到的“Fugitive-2D”，找到开发者官方指向的 [FugitiveTheGame/Fugitive](https://github.com/FugitiveTheGame/Fugitive)。[官方项目介绍](https://darkrockstudios.com/projects/fugitive)描述其为俯视2D多人躲藏追逐游戏，支持局域网/线上游玩。本文以此作为候选；若用户实际指另一仓库，应替换来源后重新核查。

工作区 `类似app` 目前存放的是 Fugitive **3D** Windows客户端和服务器运行文件，不是本轮2D项目的源码，不能将两者混记为相同复用来源。

## 3. 推荐采用方式

保留已确认的Java/libGDX + Java权威服务器 + WebSocket方案，将Fugitive列为**优先阅读的同类开源游戏参考**。先学习能服务当前需求的结构，若发现适合的独立算法，再选择性移植。由于语言和引擎不同，整项目直接复用不是本方案的实现路线；切换Godot需要单独评估并重新决定，不能由某位成员或AI擅自改变。

| 类别 | 在本项目中怎样使用 | 怎样记录成果 |
|---|---|---|
| 开源库直接依赖 | libGDX是已选框架；Java-WebSocket为网络库候选，先验证与Android环境兼容 | 依赖坐标、锁定版本、许可证、实际调用模块；不将库功能算成自研 |
| 结构参考后独立实现 | 阅读Fugitive角色、地图、页面和网络组织，整理适用的职责分离思路，用Java实现自己的规则和契约 | 原结构→本项目结构对照、未采用内容、自己的实现及测试；称“参考后实现” |
| 算法/代码移植 | 确认某个具体函数适用后，从GDScript改写到Java并验证差异 | 固定commit、源文件/函数、目标文件、修改说明、许可/署名、测试；称“移植改造” |
| 仅玩法借鉴 | 参考追逐、搜索、逃生体验，按本项目需求设计 | 写玩法来源，不写“复用了源码” |

不预先设定复用代码行数或比例，不为凑比例搬入无关模块。AI翻译源代码仍是源码移植，不自动成为独立原创实现。

## 4. 三人的源码阅读与适配任务

以下入口由仓库目录、README或project.godot确认存在；是下一步阅读清单，不代表已确认这些脚本内部算法可复用。

| 任务 | 阅读入口 | 需要回答的问题 | 对应Light Chase位置 | 当前状态 |
|---|---|---|---|---|
| OS-A1 角色结构 | actors/player/Player.gd、actors/hider/Hider.gd、actors/seeker/Seeker.gd | 角色共有状态与特殊行为怎样分离？哪些依赖Godot节点？有无适合独立测试的几何逻辑？ | game-core；规则投影与几何 | 待读具体源码 |
| OS-A2 地图结构 | README、maps/base/BaseMap.tscn及maps目录 | 地图、出生点、墙和目标如何组织？怎样转换成我们自己的数据配置？ | game-data；地图加载/校验 | 已读README，场景待读 |

| OS-B2 平滑显示 | global/InterpolatedVector.gd | 输入和输出是什么？是否能抽离节点/时钟依赖？如何处理对象隐藏？ | client-network或client-core的显示插值 | 待读，不承诺直接使用 |

每人产出一页阅读记录：来源与commit、职责图或流程、可借鉴点、不适用点、拟采用方式、目标模块、验证办法。B汇总清单，A确认不改变玩法/权限，C确认触控与表现可用。全部任务不要求先完整运行或翻译原游戏。

## 5. 与现有接口契约的关系

现有MatchEngine、ClientGateway、PlayerView和WebSocket协议继续作为Light Chase接口基线，不把Fugitive内部网络消息或节点引用暴露给其他成员。

- 原项目角色/节点结构只作为参考，客户端依旧不能拥有权威位置、交付、标记与胜负。
- 任何借来的同步机制都必须满足“服务端发送前过滤隐藏信息”；原作是否满足仍需阅读验证。
- 引擎自带碰撞、灯光、RPC等能力不能假装只翻译几个函数就能迁移。先列出依赖，再决定重写或替换。
- 原项目的队伍人数、载具、自动发现、道具、其他地图或额外输入不会自动进入V1范围。
- 本项目三次标记、保护状态、三组取送、丢弃、出口开放和同帧结局优先级按已确认需求实现，并分别验证。没有完成源码比对前，不声称这些机制在所有其他游戏中都不存在。
- 如阅读后发现现有架构需要改动，先提交具体差异和理由，同步修改三方契约；不由某一个模块私自换接口。

## 6. 许可与来源记录

Fugitive根目录MIT条款允许使用和修改等用途，并要求在软件副本或重要部分中保留其版权及许可声明。实际采用时保存对应版本完整LICENSE及必要声明；不要只留一个仓库超链接。[Fugitive LICENSE](https://github.com/FugitiveTheGame/Fugitive/blob/main/LICENSE)

libGDX和网络库也应记录各自实际使用版本的许可文件；初步来源见[libGDX LICENSE](https://github.com/libgdx/libgdx/blob/master/LICENSE)和[Java-WebSocket LICENSE](https://github.com/TooTallNate/Java-WebSocket/blob/master/LICENSE)。不要因为Fugitive采用MIT就对所有依赖和素材统一标MIT。

代码、地图、美术、字体、音频分别记录来源与许可；采用某张图片不等于自动采用该项目代码，也不等于根目录许可已覆盖所有外部素材。自制占位图可以先完成V1。

使用[开源复用登记表](07_开源复用登记表.md)记录每项状态：候选/已阅读/拟采用/已移植或已依赖/已验证/不采用。真正引入时再创建或补充项目根目录THIRD_PARTY_NOTICES及对应许可证副本；不提前写“已集成”声明。

## 7. S0新增检查与最终交付

S0增加“候选源码审核”小任务：固定计划阅读的commit，核对对应LICENSE，三人完成各自入口阅读，决定实际复用方式。它阻塞未经核查的源码导入，不阻塞编译工程壳、建立契约或独立实现基础规则。

| 验收 | 通过条件 |
|---|---|
| OS01 | 每个实际依赖/复制/移植项都有版本或commit、来源、目标路径、负责人和许可记录 |
| OS02 | 结构参考与源码移植分开标注；尚未采用项不写成已完成 |
| OS03 | 实际复制/移植文件保留适用声明，交付包中包含应附的许可/说明 |
| OS04 | 移植函数有对应测试，并通过本项目规则/权限/设备环境测试，原项目能运行不能替代此项 |
| OS05 | 三人分别说明复用了什么、改造了什么、自行实现了什么；与Git提交及测试证据一致 |

最终报告应按“基础设施复用、同类游戏参考、具体移植、团队新增工作”四部分陈述。当前可用措辞为：Light Chase计划使用libGDX作为框架，以Fugitive作为同类开源参考，按自身需求独立实现权威规则与联机协议；具体代码移植范围待阅读后决定。不得提前写成“基于Fugitive完成二次开发”。
