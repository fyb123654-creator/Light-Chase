## 二、架构设计与核心机制

### 1. 线程模型与回调串行化

- **向 C 侧彻底屏蔽网络细节**：C 侧开发者和 UI 逻辑无需感知 WebSocket 连接细节、JSON 序列化/反序列化（WireCodec）、网络 I/O 线程和心跳定时器。
- **锁与并发模型**：
  - 网关对外暴露的接口（`connect`, `selectRole`, `setReady`, `submitInput`, `returnToLobby`, `leaveRoom`, `background`, `close`）均为非阻塞且 `synchronized (this)`；
  - WebSocket 事件线程回调（`onOpen`, `onMessage`, `onClose`, `onError`）和网关内部定时器（`clock`，调度 `pulse`）均在 `synchronized (this)` 临界区内有序执行；
  - 同一个网关实例内串行处理状态与消息；回调也可能同步发生在调用线程，C仍须入队到渲染线程，不能在回调中阻塞或重入网关。
- **严格异常隔离**：
  - 统一封装 `notifySession`, `notifyControl`, `notifyConnection`, `notifyRoom`, `notifyView`, `notifyResult`, `notifyError`；
  - 每个 listener 回调入口均包裹 `try-catch (Throwable)`，外部 UI 或 listener 实现若抛出未检查异常（`RuntimeException`、`Error` 等），异常被安全捕获并隔离，绝不会击穿导致网络线程崩溃或终止 `ScheduledExecutorService` 定时器。

### 2. 连接状态机与生命周期流转

网关维护完整的连接状态机（`ConnectionStatus.state`）：
```
DISCONNECTED -> CONNECTING -> HANDSHAKING -> JOINING -> CONNECTED -> (SUSPECT <-> CONNECTED) -> CLOSED
```

1. **DISCONNECTED**：初始或尚未调用 `connect` 时的状态。
2. **CONNECTING**：`connect(options, listener)` 调用后先触发 `onSession(null)`，随后进入 `CONNECTING`，开始底层 WebSocket 连接。
3. **HANDSHAKING**：WebSocket `onOpen` 握手成功，发出 `HELLO`。
4. **JOINING**：服务端下发 `WELCOME` 且通过版本、哈希校验后，发布 `onSession(SessionInfo)`，进入 `JOINING` 并自动发送 `JOIN_ROOM`。
5. **CONNECTED**：收到首个 `ROOM_STATE`，确认加入房间成功，触发 `onConnection(CONNECTED)`，之后下发 `onRoom(room)`（确保 `onSession` 先于 `onRoom`）。
6. **SUSPECT**：连续 3000ms 未收到服务端任何有效数据包，且当前为 `CONNECTED` 时触发。通知 `listener.onConnection(SUSPECT)`，同时将有效输入清零，暂停输入推流；SUSPECT期间每帧submitInput只观察释放，不缓存有效移动/按住/drop，不刷新输入租约或分配dropId。
7. **CONNECTED（恢复）**：处于 `SUSPECT` 状态时，一旦收到来自服务端的任何合法数据包（如 PONG、ROOM_STATE、SNAPSHOT 等），恢复为 `CONNECTED`，有效输入仍保持零；中断前/期间仍活动的移动、交互和drop分别要求回中立/释放后重新操作，方向变化不算释放；已在SUSPECT释放且未再按的控制允许恢复后新按。
8. **CLOSED**：由客户端本地主动调用 `close()`/`background()`、服务端断开 `onClose`、或 5000ms 超时判定 `CONNECTION_LOST` 后触发。清理定时器、套接字、取消未决控制请求为 `CANCELLED(CONNECTION_CLOSED)`，并触发 `onSession(null)` 与 `onConnection(CLOSED, reason)`。

### 3. 健康监测与心跳逻辑

- **1000ms 心跳**：`WELCOME` 校验成功后，`pulse()` 每隔 1000ms 向服务端发出 `HEARTBEAT(nonce)`，并将 `nonce` 登记入队列。
- **PONG 原样校验**：收到服务端的 `PONG` 消息时，必须严格验证返回的 `nonce` 与最近发送的 `HEARTBEAT` 匹配。若收到未识别或篡改的 nonce，判定为协议违规 `BAD_MESSAGE` 并关闭连接。
- **3000ms SUSPECT 判定**：距离上次收到有效服务端数据包达 3000ms，转入 `SUSPECT`，推流暂停，输入归零。
- **5000ms 超时处理**：连续 5000ms 未收到服务端数据包，触发 `onError(new GatewayError("CONNECTION_LOST", "No server response for 5 seconds", true, null))`，并自动执行 `close()` 进入 `CLOSED`。

### 4. 250ms 输入租约与 20Hz 采样控制

- **常规 20Hz 推流**：在对局阶段（`phase == RoomPhase.RUNNING` 且非 `SUSPECT`）下，网关定时器以 50ms（20Hz）周期定时发送 `INPUT` 消息。
- **边沿触发与瞬时脉冲**：
  - 当 `interactHeld` 发生跳变（按下或松开），或者 `dropPressed == true` 时，无需等待 50ms 定时，立即向服务端发送当前输入帧；
  - 发送后重置 50ms 计时起点，避免产生密集脉冲帧。
- **250ms 租约到期归零**：
  - 若 C 侧连续 250ms 未调用 `submitInput`，网关触发租约到期逻辑：向服务端发送**一次**零向量（`moveX=0.0, moveY=0.0, interactHeld=false, dropId=null`），并清空待发送的 drop 脉冲；
  - 租约到期后，定时器暂停冗余推流，直到 C 侧恢复调用 `submitInput`，网关重置租约状态并恢复采样。
- **drop 脉冲单调分配与防重发**：
  - `dropPressed` 是瞬时操作，网关内部为每次丢弃分配单调递增的 `dropId`（1, 2, ...）；
  - 发送后立即清空 drop 标记，后续常规帧与定时帧中的 `dropId` 严格置为 `null`，杜绝重复发送同一 dropId。

### 5. 对局结算与 RESULT_ACK 自动响应

- 收到服务端广播的 `GAME_OVER`（携带 `MatchResult`）后：
  1. 立即置 `running = false`，输入重置为零向量，彻底停止常规推流；
  2. 锁定当前matchId的首个完整MatchResult与resultId；
  3. 自动向服务端回复 `RESULT_ACK(resultId, matchId)`；
  4. 回调 `listener.onResult(result)` **恰好一次**；
  5. 全部9字段一致重发仅ACK；同ID异内容或同局另一个ID保留首个，不ACK争议包、不改返回引用、不回调，每局最多一次可恢复RESULT_MISMATCH诊断。新局/新连接清锁。

### 6. 快照与房间接收边界（B-F01/F02）

- SNAPSHOT包络/body/current matchId必须关联自身身份与房间角色；只交付更高tick，FINISHED后的首次终局更新可同tick，重复/倒退不交付；不依赖终局快照必到，GAME_OVER后停止旧视图，新局清tick/输入。
- ROOM_STATE绑定握手身份、房间/资源、成员唯一性、角色/ready/returned/局号与阶段；旧revision忽略，同revision同内容幂等、异内容拒绝；允许合法缺失中间更新，已结束matchId不能重新RUNNING。

### 7. 防御性安全与边界

- **重复连接拦截**：若网关处于连接或活跃状态，重复调用 `connect` 将立即回调传入 listener 的 `onError(new GatewayError("ALREADY_CONNECTED", ...))`，且绝不建立多余会话或破坏已有连接。
- **`close()` 幂等性**：若网关已处于 `CLOSED` 状态，再次调用 `close()` 自动跳过，不重复触发 `CLOSED` 或 `onSession(null)` 回调。
- **`background()` 约定**：置输入为零向量，向服务端发送 `LEAVE_ROOM(reason=BACKGROUND)`，随后安全执行本地 `close()`。

### 1. 新增测试集（`ClientGatewayHealthTest`）

在 `client-network/src/test/java/com/lightchase/network/ClientGatewayHealthTest.java` 中实现了针对网关全链路行为的 11 项深度单测/集成测试：
1. `fullStateMachineTransitionTest`：验证从 `CONNECTING` 到 `HANDSHAKING`、`JOINING`、`CONNECTED` 以及最终 `CLOSED` 的顺序跃迁与 `onSession` 语义；

3. `suspectAfter3SecondsNoPacketsAndRecoveredOnPacket`：验证 3000ms 超时转入 `SUSPECT`，以及服务端后续到达包后立即恢复 `CONNECTED`；
4. `connectionLostAfter5SecondsNoPackets`：验证 5000ms 无包触发 `CONNECTION_LOST` 错误并安全置为 `CLOSED`；
5. `inputLease250msTimeoutSendsZeroVectorOnce`：验证 250ms 无输入时发送一次零向量且后续不重复发送，恢复输入后采样正常重启；
6. `dropPulseMonotonicAllocationAndClearTest`：验证瞬时 drop 脉冲单调分配 dropId（1, 2）及随后的帧立即将 `dropId` 置 `null`；
7. `gameOverStopsInputAndRepliesResultAckTest`：验证 `GAME_OVER` 停止推流、单次回调 `onResult` 以及自动回复 `RESULT_ACK`；
8. `duplicateConnectReportsAlreadyConnected`：验证重复 `connect` 报错 `ALREADY_CONNECTED` 且不影响原连接；
9. `closeIdempotencyTest`：验证连续多次调用 `close()` 的无副作用幂等性；
10. `exceptionIsolationTest`：验证恶意 listener 在所有方法中抛出 `RuntimeException` 时，网关网络线程与定时器均不崩溃并正常处理后续协议；
11. `backgroundSendsLeaveRoomAndClosesLocally`：验证 `background()` 发送 `LEAVE_ROOM(reason=BACKGROUND)` 并本地关闭。

## 四、给 C 侧（Android/client-core）的调用说明与已知边界

1. **非阻塞与线程投递约定**：
   - C 侧在任何线程均可安全调用 `ClientGateway` 的所有方法；
   - 网关下发的所有回调（`onSession`, `onControl`, `onConnection`, `onRoom`, `onView`, `onResult`, `onError`）均由网关内部串行触发。C 侧（LibGDX）在接收到回调时，应将其推入渲染线程队列（如 `Gdx.app.postRunnable`）处理显示与交互，避免在回调内部执行耗时较长的阻塞操作。
2. **输入采样建议**：
   - 在对局状态（`RUNNING`）下，C 侧每帧轮询触摸摇杆并调用 `submitInput(frame)`；
   - 交互按键发生状态切换或按下丢弃按键时，立即调用 `submitInput`；
   - 玩家双手离开屏幕（停止调用 `submitInput`）超过 250ms，网关会自动向服务端下发一次零向量，服务端将自动释放交互和位移，C 侧无需额外实现防卡键定时器。
3. **当前B6配合边界**：
   - RESULT_ACK只停止结果重发，不重置大厅；RETURN_LOBBY确认后以ROOM_STATE为准；结果重发/返回/新局已有实现与回归，双Android仍未验收；
   - `returnToLobby()` 目前要求具有有效的 `resultId`（即处于结算期），未结算时调用将在本地回调 `FAILED(INVALID_PHASE)`。
