本文的实现范围、线程描述和测试数量是 B1 交付时的记录。B2 后续已将服务端改为单一逻辑线程，并修正错误策略；当前服务端说明见 [B2 实现与交接](../server/B2_实现与交接.md)。

本次以 B1 为独立交付：保留已有 DTO、接口及已锁定依赖，补齐双向消息结构校验和测试。只修改 `client-network`、`server`；构建改动限于 `client-network/build.gradle` 的测试资源配置。没有改动玩法、地图、Android 页面或线上字段，`protocolVersion` 保持 1。

## 1. 从哪里读代码

| 入口 | 作用 |
|---|---|
| `contracts/.../ClientGateway.java` | C 调用的进程内接口：连接、选角、准备、输入、退出等 |
| `contracts/.../GatewayListener.java` | B 回给 C 的身份、控制请求状态、房间、视图、结果与错误 |
| `client-network/.../WireCodec.java` | JSON 包络编解码；提供客户端消息和服务端消息的校验入口 |
| `client-network/.../WireJson.java` | 严格读取一个 JSON 对象，拒绝重复键、非法 JSON、尾随内容和过深嵌套 |
| `client-network/.../MessageSchema.java` | 对照 v1 消息目录，验证发送方向、关联字段和 body 结构 |
| `client-network/.../BodyValidator.java` | 递归验证 RoomState、PlayerView、MatchResult 等 DTO 的字段、类型、枚举和可空值 |
| `client-network/.../WebSocketClientGateway.java` | 手机端真实网络入口；接收消息时使用 `decodeServer()` |
| `server/.../LobbyServer.java` | 服务端接收入口；先解析包络及检查版本，再调用 `validateClient()` |

表中 `...` 代表 `src/main/java/com/lightchase` 下的对应包目录。共享接口仍以契约 R2 为准。

`decode()` 只验证严格 JSON 和通用包络，不能把它当作完整消息验证。完整接收入口是 `decodeClient()`、`decodeServer()`，或先 `decode()` 再按方向调用 `validateClient()` / `validateServer()`。分两步允许服务器在 body 不合法时仍关联已解析的 requestId。

`encode()` 只序列化调用方提供的可信数据，不负责会话或玩法判断。发送 SNAPSHOT 时应由 B4 取得 A 的 `PlayerView`，不得传入内部 MatchState。接收端严格结构校验也不能替代发送端的信息过滤。

## 2. 一条消息如何流动

客户端连接后发送 HELLO，服务器验证协议及资源哈希后返回 WELCOME。客户端获得身份，再发送 JOIN_ROOM；服务器返回 ACK 和 ROOM_STATE。

```text
C 调用 ClientGateway.connect()
  → WebSocketClientGateway 建立连接并发送 HELLO
  → LobbyServer.onMessage()
  → WireCodec.decode()：严格 JSON、包络和版本
  → validateClient()：消息方向、关联字段、body
  → 现有大厅业务检查与处理
  → WELCOME / ACK / ROOM_STATE
  → 网关 decodeServer()、本地状态检查
  → GatewayListener 回调给 C
```

客户端可发 9 种消息：HELLO、JOIN_ROOM、SELECT_ROLE、SET_READY、INPUT、HEARTBEAT、LEAVE_ROOM、RETURN_LOBBY、RESULT_ACK。

服务端可发 7 种消息：WELCOME、ACK、ERROR、ROOM_STATE、SNAPSHOT、GAME_OVER、PONG。

消息使用 `v/type/seq/requestId/matchId/body` 六字段包络。控制请求携带 requestId；对局输入、视图和结果等携带 matchId；广播和心跳没有 requestId。具体组合按原接口契约第 3–5 节检查。

B1 能验证 INPUT、SNAPSHOT 等消息的结构，不表示服务端已支持运行中的对局。当前 SET_READY(true) 仍按骨架返回未实现，准备和倒计时属于 B3。

## 3. 线程在哪里

- Codec、严格 JSON 解析和结构校验不创建线程，也不读取游戏时钟；它们在调用者所在的线程执行。
- 网关的 WebSocket 回调与定时任务通过现有网关锁串行访问状态。Listener 回调可能出现在网络线程、定时线程或调用网关方法的线程。
- C 应把 Listener 数据排队交给 libGDX 渲染线程；不要在回调里阻塞、重入调用网关或直接操作渲染对象。
- 服务器目前仍是带 synchronized 的大厅回调。房间逻辑线程、固定步调度及引擎调用属于 B3/B4，本次没有把大厅线程模型冒充为完整对局模型。

## 4. 本次补齐什么

- 严格 JSON：拒绝重复包络/嵌套键、注释、单引号、尾随对象；按 UTF-8 字节执行 64KiB 上限，并限制解析嵌套深度为 64。
- 按发送方向验证全部 16 种 v1 消息，检查精确字段集合及关联字段；拒绝客户端伪造身份、坐标、胜方等额外字段。
- 数值检查拒绝非有限 double、越界 long、类型隐式转换；显式 null 与缺失字段分别处理。
- PlayerView 继续使用原 DTO：POLICE 的 thief 必须显式 null，THIEF 必须具有私有对象；递归拒绝额外隐藏状态字段。
- 网关遇到其他协议版本，明确报告 VERSION_MISMATCH 并关闭，修复原先静默丢弃的问题。其他版本 body 不按 v1 猜测解释。
- 原 `room-lobby.json` 样例经 Gradle 放到测试 classpath，测试不再用 `../docs/...` 依赖进程启动目录。

本次没有增加/删除/改名 DTO 字段，也没有修改线上枚举或其语义，因此没有引入协议版本变更。新增代码是既有 v1/R2 契约的校验实现。房间阶段、角色权限、ID 关联、移动范围、结果一致性等业务检查仍由接收状态机在后续任务落实。

## 5. 测试怎么跑

先确保 Gradle 使用 JDK 21（源码编译目标仍为 Java 17），然后在项目根目录运行。

macOS/Linux：

```sh
sh gradlew :contracts:test :client-network:test :server:test --console=plain
sh gradlew checkJvm --console=plain
```

Windows PowerShell：

```powershell
.\gradlew.bat :contracts:test :client-network:test :server:test --console=plain
.\gradlew.bat checkJvm --console=plain
```

只跑新增的协议与假端点测试：

```sh
sh gradlew :client-network:test --tests '*ProtocolContractTest' --tests '*WireJsonTest' --tests '*GatewayProtocolBoundaryTest' :server:test --tests '*LobbyProtocolBoundaryTest' --console=plain
```

`ProtocolContractTest` 用构造消息及真实 DTO 检查双向目录、字段和往返一致性；`GatewayProtocolBoundaryTest` 用故意返回错误消息的假服务器测试真实网关；`LobbyProtocolBoundaryTest` 用原始假客户端测试真实服务端。网络边界测试不实例化 A 的引擎。协议样例在 `src/test/resources/protocol/`，坐标和哈希都是测试数据。

本机没有改全局 Java 设置。JDK 21 缓存在 `/Users/fyb/.cache/lightchase-tools/jdk21/Contents/Home`；复现本次环境时，在上述 Gradle 命令前加 `JAVA_HOME=/Users/fyb/.cache/lightchase-tools/jdk21/Contents/Home`，并给 Gradle 加 `-Dorg.gradle.java.installations.paths=/Users/fyb/.cache/lightchase-tools/jdk21/Contents/Home`。其他成员使用自己的 JDK 路径。
