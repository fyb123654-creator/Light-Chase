## 入口、线程与数据流

`LobbyServer` 的 `lightchase-lobby-logic` 线程拥有所有房间、会话、MatchRuntime和A引擎。WebSocket回调只入队；输入结构由原Codec校验，随后按会话绑定身份、当前房间/阶段/matchId与角色校验。默认构造器仍显式使用 `V1EngineFactory`，所有假引擎/故障注入都在测试或全局探针，发布包不含测试入口。

新增 `MatchRuntime` 管理一局的调度与传输输入，不实现移动/碰撞/光照/任务/胜负规则：

- 整数累计 `elapsedMs * tickRate`，1000累计单位换一个1/30秒逻辑步；每轮最多5步，余量保留。累计积压严格超过1秒（30步）时停止推进并调用A的abort；不浮点累积33ms、不跳过逻辑步。
- 每个步边界一次取走当时全部FIFO命令和去重Departure，之后的命令留给下步。按下、释放和drop不被“只留最终输入”合并。A自行按契约归并并决定一次移动/交互。
- inputSeq从1起严格递增，旧输入丢弃并按连接每秒最多反馈一次STALE_INPUT。dropId按本局玩家单调高水位去重；新input携带旧drop时仅清掉重复drop，其连续移动/释放仍有效。非法input不推进序号/drop高水位、不刷新输入租约。
- 最近合法输入后250ms，达到下一逻辑步边界时追加零向量、held=false、dropId=null的内部命令，沿用最后inputSeq，且每次租约只释放一次。心跳只续连接活性，不延长输入租约。
- ackInputSeq只在A成功消费该步FIFO后更新；viewFor返回的语义视图不改动，只复制补serverTimeMs/ackInputSeq。

RUNNING和首个tick=0视图仍按B3顺序发送。常规视图在偶数tick发送（15Hz）；A报告首步/可见性变化时立即发双方各自viewFor，终局立即处理。没有完整MatchState序列化，也没有在B重新推断可见性。

## Departure、异常和一次结果

QUIT/BACKGROUND/确认超时/onClose及已关闭socket都先保留会话和成员，把Departure与归零输入排到下一步。相同玩家只排一次，先收到的明确退出原因不被随后onClose覆盖。两人同一逻辑步离开交给A处理BOTH_LEFT；正常玩法结束优先级也由A处理。

RUNNING的LEAVE_ROOM不会提前ACK或删除成员；相同待处理requestId重放等待原终态，冲突内容仍报REQUEST_ID_REUSED。A提交唯一结果后，房间转FINISHED并广播revision，尽力发送终局角色视图，再向仍可达玩家发送一次GAME_OVER，最后发送退出方ACK并解除成员/关闭。后到离开不改既有结果。终局视图失败不阻止已确认结果投递。

step或运行中viewFor抛受控异常时在同一逻辑线程调用A.abort。abort返回确认结果则走相同FINISHED路径；abort也异常时仅对该房间发致命SERVER_ERROR并关闭，不伪造胜负，不影响其他房间。调度积压同样使用A.abort，B不自行构造MatchResult。

## 协议与客户端交接

沿用v1包络及DTO，无新增字段。输入需当前RUNNING matchId；错局为STALE_MATCH，非运行期为INVALID_PHASE，越界/零inputSeq/dropId为INVALID_INPUT，警察held/drop为INVALID_ACTION，旧inputSeq为STALE_INPUT。结构非法仍走原B1的BAD_MESSAGE规则。

例：`INPUT(matchId=current, inputSeq=1, moveX=1, moveY=0, interactHeld=false, dropId=null)` → 本步FIFO → A.step → `SNAPSHOT(ackInputSeq=1)`。无合法输入250ms后B追加同序号归零释放。QUIT → A.step(departures) → ROOM_STATE(FINISHED) → 可选终局SNAPSHOT → GAME_OVER → ACK → 关闭；客户端必须独立处理GAME_OVER，不依赖终局视图存在。

ClientGateway签名及回调线程约定未变；已有网关可发送submitInput并接收onView/onResult，C仍须将回调入渲染队列。完整网关健康/生命周期行为留B5。当前网关自动发出的RESULT_ACK尚由服务器拒绝INVALID_PHASE，返回大厅/重开也不可用，留B6；不能据此宣称完整用户流程联调完成。
