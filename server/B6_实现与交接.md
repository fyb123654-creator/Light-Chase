## 二、核心机制与状态机流转设计

### 1. GAME_OVER 确认重发与 RESULT_ACK 消费
- **确认状态跟踪**：在 `Session` 中新增 `boolean resultAcked` 与 `long lastGameOverSentAt`；
- **首次投递**：对局结束流转至 `RoomPhase.FINISHED` 时，服务端广播最新的 `ROOM_STATE`，向所有活跃玩家发送终局视图（可选）并立即投递首个 `GAME_OVER(MatchResult)` 消息，初始化 `session.resultAcked = false`，记录投递时间戳 `session.lastGameOverSentAt = now`；
- **周期重发**：服务端主定时轮询（`SESSION_SCAN_MS = 10ms`）驱动 `advanceFinishedRooms(now)`，对处于 `FINISHED` 阶段且未离场、未确认（`!session.resultAcked`）的活跃玩家，每隔 1000ms（`now - lastGameOverSentAt >= 1000`）重复向其重发 `GAME_OVER` 消息；
- **RESULT_ACK 消费**：
  * 客户端接收 `GAME_OVER` 后自动发送 `RESULT_ACK(resultId, matchId)`（`client-network` 已实现）；
  * 服务端验证 `matchId` 与 `resultId` 是否与当前房间对局匹配：
    - 若 `matchId` 或 `resultId` 不匹配，反馈 `ERROR(code="RESULT_MISMATCH", fatal=false)`；
    - 若匹配，标记该连接 `session.resultAcked = true`，停止后续对该连接的 `GAME_OVER` 重复投递；
    - 不变更房间状态与准备状态，不返回多余错误，重复到达完全幂等。

### 2. 返回大厅（RETURN_LOBBY）与新局重开（新 matchId）
- **请求校验与幂等**：
  * 校验阶段必须为 `RoomPhase.FINISHED`，否则返回 `ERROR(code="INVALID_PHASE")`；
  * 校验 `matchId` 与 `resultId` 必须与当前对局匹配，否则返回 `ERROR(code="RESULT_MISMATCH")`；
  * 若该玩家已处于 `returned == true` 状态（重复调用 `returnToLobby()`），服务端按幂等规则处理：返回原 `ACK("RETURN_LOBBY")` 并对其单播重发 `ROOM_STATE`，不递增 `revision`，不产生多余副作用；
- **单方返回状态更新**：
  * 首次返回时，标记该玩家 `session.returned = true`（同时置 `session.resultAcked = true`），回复 `ACK("RETURN_LOBBY")`；
  * 若房间内仍有活跃玩家处于 `returned == false`，递增 `room.revision++`，广播更新后的 `ROOM_STATE`（展示各玩家的 `returned` 布尔值，阶段仍为 `FINISHED`）；
- **全员返回流转至 LOBBY**：
  * 当房间内的活跃玩家均已 `returned == true`（或者对手退出/掉线后，房间内只剩 1 人且已 `returned == true`）：
    1. 房间状态流转回 `RoomPhase.LOBBY`；
    2. 清空 `matchId = null`，解绑本局 `match` 与 `result`；
    3. 所有玩家的准备状态与返回状态重置：`ready = false`，`returned = false`，`resultAcked = false`；
    4. 玩家选择的角色槽位（`role`）**严格保持不变**；
    5. 递增 `room.revision++`，广播最新的大厅 `ROOM_STATE`；
- **新局重开**：
  * 双方在保留的角色槽位上重新调用 `SET_READY(true)`；
  * 服务端检查双方就绪后流转至 `RoomPhase.COUNTDOWN`；
  * 倒计时 90 步（3000ms）结束后，调用 `startMatch()`：生成**全新且唯一**的 `matchId`（`UUID.randomUUID().toString()`），重置各玩家状态，进入新一局 `RUNNING` 阶段；
- **旧局包拒绝（STALE_MATCH）**：
  * 当房间处于新局 `RUNNING` 时，任何携带旧 `matchId` 的 `INPUT`、`RETURN_LOBBY`、`RESULT_ACK` 请求均被服务端安全拦截并回复 `ERROR(code="STALE_MATCH", fatal=false)`，绝不会污染当前新对局。

### 3. 背压（Backpressure）、快照丢旧保新与限流防护（Rate Limiting）
- **出站快照丢旧保新（Snapshot Conflation）**：
  * 每连接维护 `OutboundMessage pendingSnapshot`；
  * 当检测到底层 WebSocket 处于发送积压/慢状态（`isBuffered(connection)` 为真）时，新的快照不会继续追加到底层发送队列，而是暂存于 `session.pendingSnapshot` 中；
  * 若底层通道尚未完成发送，后续产生的最新快照将**直接覆盖/替换**旧的未发快照；
  * 一旦底层通道缓冲区空闲，在下一次调度轮询或消息流转时，立即将这唯一的最新快照编码并投递，彻底消除慢网络时快照无限堆积和延迟累积的问题；
- **控制包与结果队列保护（Bounded Control Queue）**：
  * 控制消息（`WELCOME`, `ACK`, `ERROR`, `ROOM_STATE`, `GAME_OVER`, `PONG`）要求可靠交付；
  * 当慢客户端严重阻塞导致底层出站队列积压达 64 项（`MAX_OUTBOUND_CONTROL = 64`）时，服务端判定该慢客户端已严重脱节，安全执行 `close(connection, 1008, "OUTBOUND_QUEUE_OVERFLOW")` 终止问题会话；
- **限流防护（Rate Limiting）**：
  * 对齐 02 契约第 9 节：
    - **输入限流**：每秒最多允许 60 条 `INPUT` 消息（60/s）；
    - **控制请求限流**：每秒最多允许 10 条控制请求（`requestId != null`，如 `SELECT_ROLE`, `SET_READY`, `RETURN_LOBBY` 等，10/s）；
  * 超额拦截：在 1000ms 计数窗口内超额的请求被直接拦截，反馈 `ERROR(code="RATE_LIMITED", fatal=false)`（对应客户端 `recoverable=true`）；
  * 持续超额惩罚：若客户端持续超额达 3 秒（`now - violationStart >= 3000`），服务端判定为恶意循环或异常攻击，反馈 `ERROR(code="RATE_LIMITED", fatal=true)` 并以状态码 1008 安全关闭连接。

4. `singleRemainingPlayerReturnedTransitionsToLobby`：验证对手在结算期退出后，仅剩 1 名玩家调用 RETURN_LOBBY 时也能安全流转回 LOBBY；

9. `outboundSnapshotConflationDropsOldFrames`：验证慢网络阻塞时，服务端连续生成的多个快照被自动合并，仅保留并最终发送最新快照（丢旧保新）；
10. `outboundControlQueueBoundedAt64AndClosesSlowClient`：验证慢客户端出站队列达到 64 缓冲上限时，服务端安全断开该连接；

## 四、给 C 侧（Android/UI）与协调者的交接说明

1. **结算页返回大厅时序建议**：
   - 当 UI 收到 `listener.onResult(result)` 时，网关已发送 `RESULT_ACK`；服务端收到并校验成功后停止该连接的 `GAME_OVER` 重发；
   - 玩家点击结算界面的“返回大厅”按钮时，UI 线程调用 `gateway.returnToLobby()`；
   - 此时 `onControl` 会收到 `PENDING`，随后收到 `SUCCEEDED`（action: "RETURN_LOBBY"）；
   - UI **不应**在控制成功回调里自行切换页面，而应监听 `onRoom(room)` 回调：
     * 若 `room.phase == FINISHED` 且自己 `returned == true`，UI 可在界面上显示“等待对手返回...”；
     * 当双方均已返回，收到 `room.phase == LOBBY` 且 `matchId == null` 时，UI 自动无缝切回大厅房间界面。
2. **再来一局（Rematch）体验**：
   - 回到大厅后，双方的角色槽位（Role）已由服务端自动保留，无需重新选角；
   - 双方只需直接点击“准备”（`gateway.setReady(true)`），即可直接触发 3 秒倒计时开启新局；
   - 新局会分发全新的 `matchId`，旧局所有输入与快照缓存已自动失效。
3. **输入与控制限流建议**：
   - 客户端正常 20Hz 摇杆推流（每秒 20 帧）远低于 60/s 的限流阈值；
   - 若本地发生高频触控连击，网关层内置的边沿触发与采样定时器已有效收敛发送频率；
   - 切忌在 UI 中使用无限循环发送无等待的控制请求，避免触发服务端 `RATE_LIMITED` 保护。

## 当前首结果与设备边界

网关按matchId保留首个完整MatchResult，一致重复仅确认；任何字段或resultId冲突均不覆盖、不再次回调、不ACK争议包，返回仍引用首结果，每局一次受控诊断。新局/连接清锁，旧局包不污染第二局。实际双JVM网关两局测试不等同双Android或完整自然玩法验收；C真实接入依赖未就绪，设备出口保留未验收。
