## 2. 线程和超时

```text
WebSocket 网络线程
  onOpen / onMessage / onClose / 连接级 onError
    → dispatch 入队
    → lightchase-lobby-logic 单一逻辑线程
    → Session / Room / 请求缓存 / 响应 / 成员清理

同一个逻辑线程每 100ms 巡检超时。
```

会话、角色和房间只在逻辑线程修改，避免房间满员判断、成员退出和角色占位同时发生。启动成功/失败使用 CountDownLatch 通知 main；关闭使用幂等开关停止逻辑执行器和 WebSocket 服务。

使用单调时间，不读取系统日期。未完成 HELLO 时，3 秒截止时间固定从连接打开算起，坏消息不会推迟它。握手后，以最后一条结构合法且序号更新的消息计算 5 秒空闲期限；旧包不会续期。缓存命中的有效重发请求仍算有效收包。

处理新消息前也检查截止时间，避免超时 HELLO 恰好在两次巡检之间被接受。3 秒和 5 秒是判断阈值，实际空闲连接关闭在巡检执行时发生，不承诺操作系统实时调度。测试注入可控时钟验证阈值，不靠真实等待。

此处尚无 B4 的固定步引擎调度，也没有 B5 的 3 秒 SUSPECT 展示和 B6 的队列/速率限制。

## 3. 正常消息流程

```text
连接 ws://电脑地址:端口/game
  → HELLO（clientBuild、mapHash、configHash；首包 seq=1）
  → WELCOME（服务器生成 sessionId/playerId；协议及资源信息）
  → JOIN_ROOM（1–8 位大写字母/数字）
  → ACK
  → ROOM_STATE（大厅、成员与角色）

HEARTBEAT → PONG（回显 nonce，提供单调 serverTimeMs）
SELECT_ROLE → ACK + ROOM_STATE，角色冲突返回 ROLE_TAKEN
LEAVE_ROOM → ACK → 关闭连接、释放角色/成员、通知仍在房间的人
```

没有账号和恢复 token。新连接生成新身份，不能恢复旧会话。大厅离开不产生胜负或 GAME_OVER。SET_READY(true) 仍返回未实现；准备与倒计时留给 B3。

## 4. 房间和重复请求

- 不存在的合法房间自动创建；同房最多两人，最多八个房间。达到上限仍可加入已有且有空位的房间。
- 同连接再次加入相同房间：返回 ACK 和当前 ROOM_STATE，不增加成员、不改变 revision，也不通知其他玩家发生了不存在的变更。
- 同连接已在其他房间：返回 INVALID_PHASE。离开会关闭连接，重新连接后可加入新房间。
- 每连接保存最近 128 个合法控制请求的结果。同 requestId、消息类型、matchId 和 body 内容相同，复用原结果；JSON 字段顺序不影响内容比较。
- 同 requestId 换了内容：REQUEST_ID_REUSED，不覆盖原缓存。重放 JOIN_ROOM 成功结果时，附带当前房间视图，避免返回旧成员快照。
- 结构非法消息及旧序号不会污染合法控制请求缓存。旧序号反馈 STALE_MESSAGE，同连接每秒最多一次。
- 合法包络的新序号在 body 校验前消费；即使 body 缺字段，修正请求也应使用下一个序号。body 非法不会刷新存活时间或重置连续坏消息计数。
- 角色离开、连接关闭和发送瞬间断开均释放成员；重复 close 回调不重复清理，空房间删除。

## 5. 错误策略

| 场景 | 结果 |
|---|---|
| 连接路径不是 /game | 拒绝该端点，返回错误并关闭 |
| HELLO 前提交其他消息 | HANDSHAKE_REQUIRED，致命 |
| 3 秒内未完成握手 | HANDSHAKE_TIMEOUT，致命 |
| 协议、地图或规则不匹配 | VERSION_MISMATCH / MAP_MISMATCH / CONFIG_MISMATCH，致命，不发布 WELCOME |
| 非法房间号、房满、角色已被占用、尚未入房 | 对应业务错误，可恢复；使用新请求可重试 |
| 第九个新房间 | SERVER_BUSY，fatal=true；不踢已有成员 |
| 连续坏消息 | 前两次 BAD_MESSAGE 为非致命，第三次致命；有效新序号消息重置连续计数 |
| 超过 64KiB | MESSAGE_TOO_LARGE，立即关闭 |
| 二进制消息 | 协议只接受 JSON 文本，按坏消息处理 |
| 对局操作出现在大厅 | INVALID_PHASE；ERROR 保留原 requestId/matchId |
| 握手后 5 秒无有效新消息 | 关闭并清理大厅成员；不伪造对局结果 |

这些错误沿用现有契约。原 08 文档中记录的“BAD_MESSAGE 一律致命”和“SERVER_BUSY 为非致命”已在 B2 修复。异常消息不带堆栈或内部游戏状态。

模拟器/真机地址仍按原运行手册配置，不能把手机自身的 localhost 当成电脑。探针 PASS 只代表传输和大厅，不代表完整游戏。

## 8. B2 审查 P2 修复与复测

审查发现：首个 HELLO 的包络合法但 body 缺少 configHash，返回非致命 BAD_MESSAGE 后没有消费 seq=1，导致修正后的 seq=2/3 均被错误拒绝。初次“225 项通过”的测试集未覆盖该情况。

先新增真实 WebSocket 回归，在修改业务代码前确认失败；随后将序号检查和消费移到 body 校验之前。仍只在 body 合法时刷新 lastPacket 和重置 badMessages，不改变线上字段或玩法。

新增四项回归：

1. seq=1 缺字段 → 非致命 BAD_MESSAGE；seq=2 修正 → WELCOME；之后仍能加入房间。
2. 已消费的坏 body 序号不能复用；旧 seq=1 返回 STALE_MESSAGE，合法 seq=2 可以恢复。
3. seq=1/2/3 连续提交坏 body，第三次仍按约定致命，不能靠递增序号重置错误计数。
4. 消费坏 body 的序号不会续期；可控时钟验证空闲到 5 秒仍关闭。

原样执行用户审查脚本 `/Users/fyb/Desktop/实验1/webcoding存脚本专用/LightChaseB2ReviewProbe.java`，未修改脚本，进程状态 0。实际输出为：seq=1 得到非致命 BAD_MESSAGE，seq=2 得到 WELCOME，seq=3 因握手已经成功得到非致命 INVALID_PHASE（不是原缺陷中的致命 BAD_MESSAGE）。脚本自行关闭连接和服务器。

复测 `checkJvm :server:installDist` 通过，server 为 40 项、全项目为 229 项；`git diff --check` 通过。未开展 B3 或双 Android 设备测试。
